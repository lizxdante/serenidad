# HU-01.1 — Creación de Cuentas en Servicios Externos

## Descripción General

Esta historia de usuario establece las cuentas fundacionales en los cinco proveedores SaaS que componen la infraestructura de la plataforma. Son los pilares sobre los que se construirá todo lo demás: fuente de verdad del código, cómputo en la nube, DNS y protección de perímetro, almacenamiento de objetos para backups, y entrega de correo transaccional.

### Inventario de servicios y su función

| Servicio | Rol en la plataforma | Interacción posterior |
|---|---|---|
| **GitLab** | Source of Truth: código, CI/CD, Container Registry | `flux bootstrap`, pipelines CI, `kubectl` via deploy tokens |
| **Hetzner Cloud** | Proveedor de cómputo: VPS CX32, Floating IP | `hcloud` CLI, Cloud Controller Manager de Kubernetes |
| **Cloudflare** | DNS autoritativo, proxy TLS, Workers/Pages edge | `wrangler`, `cert-manager` DNS-01 challenge |
| **Backblaze B2** | Object storage S3-compatible para WAL y backups PG | CloudNativePG Barman via credenciales S3 |
| **Resend** | SMTP transaccional para Ory Kratos | Configuración de courier en Helm values |

## Ejecución Detallada

### T-01.1.1 — GitLab

**Interacción:** Consola web de GitLab (`gitlab.com`).

1. Crear cuenta o iniciar sesión en [gitlab.com](https://gitlab.com).
2. Crear un **Grupo** llamado `serenidad`.
3. Dentro del grupo, crear un nuevo proyecto **privado** llamado `serenidad-platform`. No inicializar con README ni `.gitignore` — se realizará programáticamente en HU-01.4.
4. En **Settings → CI/CD → Runners**, confirmar que los Shared Runners están habilitados.

**Generar Personal Access Token (PAT):**

- Ir a: Perfil de usuario → **Edit Profile → Access Tokens → Add new token**.
- Nombre: `serenidad-admin-pat`
- Scopes requeridos: `api`, `read_repository`, `write_repository`, `read_registry`, `write_registry`
- Guardar el valor en el Password Manager con la clave `GITLAB_TOKEN`. Solo se muestra una vez.

**Generar Deploy Token para Kubernetes:**

- Ir a: Proyecto `serenidad-platform` → **Settings → Repository → Deploy tokens**.
- Nombre: `k8s-registry-puller`
- Scopes requeridos: `read_registry`, `read_repository`
- Guardar el *Username* generado (ej. `gitlab+deploy-token-123`) y el *Token* en el PM como `GITLAB_DEPLOY_TOKEN_USER` y `GITLAB_DEPLOY_TOKEN`.

**Verificación:**
```bash
curl -s --header "PRIVATE-TOKEN: ${GITLAB_TOKEN}" \
  "https://gitlab.com/api/v4/user" | jq '.username'
# Debe retornar tu username de GitLab sin errores 401/403
```

### T-01.1.2 — Hetzner Cloud

**Interacción:** Consola web de Hetzner Cloud (`console.hetzner.cloud`).

1. Crear cuenta en [hetzner.com/cloud](https://www.hetzner.com/cloud). Requiere verificación de identidad (puede tardar entre 1 y 24 horas).
2. Una vez activa, crear un **Proyecto** llamado `serenidad-production`. Este proyecto agrupará servidores, IPs flotantes, volúmenes y redes.

**Generar API Token:**

- Dentro del proyecto → **Security → API Tokens → Generate API Token**.
- Nombre: `serenidad-ops`
- Permisos: **Read & Write**
- Guardar en el Password Manager como `HCLOUD_TOKEN`. No se puede recuperar después de cerrar el modal.

**Verificación:**
```bash
curl -s -H "Authorization: Bearer ${HCLOUD_TOKEN}" \
  "https://api.hetzner.cloud/v1/servers" | jq '.servers | length'
# Retorna 0 (sin servidores aún). Cualquier respuesta JSON válida confirma el token.
```

### T-01.1.3 — Cloudflare

**Interacción:** Consola web de Cloudflare (`dash.cloudflare.com`).

1. Crear cuenta en [cloudflare.com](https://www.cloudflare.com).
2. Agregar el dominio `sereni.dad`: **Add a Site** → Plan **Free**.
3. Cloudflare proveerá dos Nameservers (ej. `hazel.ns.cloudflare.com`). En el registrador del dominio, reemplazar los NS actuales por los de Cloudflare. La propagación tarda entre 1 y 48 horas.
4. Una vez el estado muestre **Active**, extraer del panel **Overview** del dominio: **Zone ID** y **Account ID** (columna derecha). Guardar en PM como `CF_ZONE_ID` y `CF_ACCOUNT_ID`.

**Generar API Token con permisos mínimos necesarios:**

- Ir a: Perfil → **API Tokens → Create Token → Custom Token**.
- Nombre: `serenidad-ops`
- Permisos requeridos:
  - `Zone → DNS → Edit` — para `cert-manager` DNS-01 challenge y gestión de registros A/CNAME
  - `Account → Cloudflare Pages → Edit` — para deploy de la SPA web
  - `Account → Workers Scripts → Edit` — para deploy del BFF
- Zone Resources: `Include → Specific Zone → sereni.dad`
- Guardar en PM como `CF_API_TOKEN`.

**Verificación:**
```bash
# Verificar token activo
curl -s -X GET "https://api.cloudflare.com/client/v4/user/tokens/verify" \
  -H "Authorization: Bearer ${CF_API_TOKEN}" \
  -H "Content-Type: application/json" | jq '.result.status'
# Debe retornar: "active"

# Verificar propagación de NS
dig sereni.dad NS @1.1.1.1 +short
# Debe mostrar nameservers de Cloudflare (*.ns.cloudflare.com)
```

### T-01.1.4 — Backblaze B2

**Interacción:** Consola B2 (`backblaze.com/b2/cloud-storage`).

1. Crear cuenta y activarla (verificar email).
2. Ir a **Buckets → Create a Bucket**:
   - Nombre: `serenidad-pg-backups`
   - Visibilidad: **Private**
   - Encryption: **Enable Server-Side Encryption** (SSE-B2)
   - Object Lock: Disabled
   - Region: `eu-central` (Frankfurt/Ámsterdam) — co-localización óptima con Hetzner Nuremberg
3. Una vez creado, obtener el **Endpoint S3** del bucket desde **Bucket Settings → Endpoint**. Formato: `s3.eu-central-003.backblazeb2.com`. Guardar en PM como `B2_ENDPOINT`.

**Generar Application Key con acceso restringido al bucket:**

- Ir a: **Account → Application Keys → Add a New Application Key**.
- Nombre: `cnpg-barman-key`
- Allow access to Bucket(s): seleccionar **únicamente** `serenidad-pg-backups`
- Type of access: Read and Write
- File name prefix: (vacío)
- Duration: sin expiración
- Copiar inmediatamente el `keyID` y la `applicationKey`. Guardar en PM como `B2_KEY_ID` y `B2_APPLICATION_KEY`.

> **Advertencia:** La `applicationKey` se muestra una sola vez. Si se pierde, se debe revocar y generar una nueva key con los mismos permisos.

### T-01.1.5 — Resend (SMTP Transaccional)

**Interacción:** Consola de [resend.com](https://resend.com).

1. Crear cuenta en [resend.com](https://resend.com).
2. Ir a **Domains → Add Domain**. Ingresar `sereni.dad`.
3. Resend proveerá registros DNS que deben añadirse en Cloudflare → **DNS → Records**:
   - Registro `TXT` para SPF
   - Registros `TXT` para DKIM (1–3 entradas según la configuración de Resend)

   > Los registros de correo **no deben usar el proxy de Cloudflare** (ícono naranja). Deben configurarse como DNS-only (ícono gris).

4. En Resend → **Domains**, hacer click en **Verify DNS Records**. Puede tardar hasta 30 minutos.

**Generar API Key:**

- Ir a: **API Keys → Create API Key**.
- Nombre: `serenidad-kratos`
- Permisos: **Sending access** (no Full Access)
- Domain: restringir a `sereni.dad`
- Guardar en PM como `RESEND_API_KEY`.

**Verificación:**
```bash
curl -X POST 'https://api.resend.com/emails' \
  -H "Authorization: Bearer ${RESEND_API_KEY}" \
  -H 'Content-Type: application/json' \
  -d '{
    "from": "noreply@sereni.dad",
    "to": ["<tu-email-de-prueba>"],
    "subject": "Verificación Resend — serenidad",
    "text": "Si recibes este correo, Resend está configurado correctamente."
  }' | jq '.id'
# Retorna un UUID si el envío fue aceptado por la API
```

## Criterios de Aceptación

| ID | Criterio | Método de verificación |
|----|----------|------------------------|
| CA-01.1.1 | GitLab PAT con scopes `api`, `read/write_repository`, `read/write_registry` activo | `GET /api/v4/user` retorna HTTP 200 con `username` |
| CA-01.1.2 | Deploy Token `k8s-registry-puller` con scopes `read_registry`, `read_repository` | Username y token almacenados en PM |
| CA-01.1.3 | Hetzner API Token Read&Write activo en proyecto `serenidad-production` | `GET /v1/servers` retorna HTTP 200 con JSON válido |
| CA-01.1.4 | Cloudflare zone `sereni.dad` con estado **Active** y NS propagados | `dig sereni.dad NS @1.1.1.1` muestra NS de Cloudflare |
| CA-01.1.5 | CF API Token con los 3 permisos requeridos y estado `active` | `/user/tokens/verify` retorna `"status": "active"` |
| CA-01.1.6 | Bucket B2 `serenidad-pg-backups` creado como **Private** con SSE habilitado | Visible en consola B2 con los atributos correctos |
| CA-01.1.7 | B2 Application Key restringida exclusivamente al bucket `serenidad-pg-backups` | Key no puede acceder a otros buckets |
| CA-01.1.8 | Dominio `sereni.dad` con estado **Verified** en Resend | Consola Resend muestra DKIM verificado |
| CA-01.1.9 | API Key de Resend válida y capaz de enviar correos desde `sereni.dad` | `POST /emails` retorna UUID del email enviado |

## Definition of Done

- [ ] Los cinco servicios tienen cuentas activas y verificadas
- [ ] Los diez secretos/tokens almacenados en Password Manager: `GITLAB_TOKEN`, `GITLAB_DEPLOY_TOKEN_USER`, `GITLAB_DEPLOY_TOKEN`, `HCLOUD_TOKEN`, `CF_API_TOKEN`, `CF_ZONE_ID`, `CF_ACCOUNT_ID`, `B2_KEY_ID`, `B2_APPLICATION_KEY`, `B2_ENDPOINT`, `RESEND_API_KEY`
- [ ] Los tokens de GitLab, Hetzner y Cloudflare verificados mediante API call exitosa
- [ ] El dominio `sereni.dad` está activo en Cloudflare (NS propagados) y verificado en Resend (DKIM OK)
- [ ] Ninguna credencial transmitida por canales inseguros (Slack, email, chat)
