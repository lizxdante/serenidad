# HU-04.1 — cert-manager v1.x + Let's Encrypt

## Descripción General

`cert-manager` es el gestor automático de certificados TLS del cluster. Se integra con Let's Encrypt mediante el protocolo ACME para emitir, renovar y revocar certificados sin intervención manual. Se despliega via GitOps (FluxCD + Helm) para mantener consistencia declarativa.

El flujo de emisión de un certificado es:

```
Traefik recibe request HTTPS →
cert-manager detecta anotación →
ACME HTTP-01 challenge a Let's Encrypt →
Let's Encrypt verifica propiedad del dominio via HTTP →
cert-manager almacena el certificado como Secret TLS en K8s →
Traefik sirve el certificado
```

Se configuran dos `ClusterIssuers`: uno de **staging** (para pruebas sin consumir la cuota de producción de Let's Encrypt, que tiene un límite de 5 certificados por dominio por semana) y uno de **producción**.

### T-04.1.2 — HelmRelease de cert-manager

```bash
cat > infra/infrastructure/cert-manager/helmrelease.yaml << 'EOF'
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: cert-manager
  namespace: cert-manager
spec:
  interval: 10m
  chart:
    spec:
      chart: cert-manager
      version: ">=1.15.0 <2.0.0"
      sourceRef:
        kind: HelmRepository
        name: jetstack
        namespace: flux-system
      interval: 1h
  install:
    createNamespace: true
    remediation:
      retries: 3
  upgrade:
    remediation:
      retries: 3
  values:
    # Instalar CRDs como parte del chart (requerido para que FluxCD gestione CRDs)
    crds:
      enabled: true
    # Webhook para validación de recursos de cert-manager
    webhook:
      enabled: true

      enabled: false
```

### T-04.1.3 — ClusterIssuers de Let's Encrypt

```bash
cat > infra/infrastructure/cert-manager/clusterissuers.yaml << 'EOF'
# ClusterIssuer de STAGING — Para pruebas
# Los certificados emitidos por staging NO son confiables por navegadores
# pero no consumen la cuota de producción de Let's Encrypt
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-staging
spec:
  acme:
    email: admin@sereni.dad
    server: https://acme-staging-v02.api.letsencrypt.org/directory
    privateKeySecretRef:
      name: letsencrypt-staging-account-key
    solvers:
      - http01:
          ingress:
            ingressClassName: traefik
---
# ClusterIssuer de PRODUCCIÓN — Para certificados reales y válidos
# Límite: 5 certificados por dominio por semana
# Usar SIEMPRE staging primero para validar la configuración
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    email: admin@sereni.dad
    server: https://acme-v02.api.letsencrypt.org/directory
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
      - http01:
          ingress:
            ingressClassName: traefik
EOF
```

### T-04.1.4 — Commitear y desplegar via FluxCD

```bash
git add infra/infrastructure/cert-manager/
git commit -m "feat(infra): deploy cert-manager and letsencrypt cluster issuers"
git push origin main

# Forzar reconciliación
flux reconcile kustomization flux-system --with-source

# Esperar a que cert-manager esté disponible (~2 minutos)
flux get helmrelease cert-manager -n cert-manager --watch
# Esperar hasta ver: Ready True
```

### T-04.1.5 — Verificar el despliegue

```bash
# 1. Los 3 pods de cert-manager deben estar Running
kubectl get pods -n cert-manager
# Debe mostrar:
# cert-manager-xxx                      1/1   Running
# cert-manager-cainjector-xxx           1/1   Running
# cert-manager-webhook-xxx              1/1   Running

# 2. Los CRDs de cert-manager deben estar instalados
kubectl get crd | grep cert-manager.io | wc -l
# Debe ser >= 6 CRDs

# 3. Los ClusterIssuers deben estar en estado Ready: True
kubectl get clusterissuers
# NAME                   READY   AGE
# letsencrypt-staging    True    Xm
# letsencrypt-prod       True    Xm

# 4. Verificar los logs sin errores
kubectl logs deployment/cert-manager -n cert-manager --tail=20 | grep -v "^I"
# No debe haber errores
```

### T-04.1.6 — Test de emisión con staging

```bash
# Crear un Certificate de prueba usando el issuer de staging
cat > /tmp/test-certificate.yaml << 'EOF'
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: test-cert
  namespace: default
spec:
  secretName: test-cert-tls
  issuerRef:
    name: letsencrypt-staging
    kind: ClusterIssuer
  dnsNames:
    - api.sereni.dad
EOF

kubectl apply -f /tmp/test-certificate.yaml

# Monitorear el proceso de emisión
kubectl describe certificate test-cert -n default
# Buscar: "Certificate issued successfully"

# Verificar el secret TLS generado
kubectl get secret test-cert-tls -n default
# Debe existir con tipo kubernetes.io/tls

# Limpiar después de verificar
kubectl delete -f /tmp/test-certificate.yaml
kubectl delete secret test-cert-tls -n default --ignore-not-found
```

**Troubleshooting:**
- Si el Certificate queda en `Pending`: verificar que Traefik está desplegado y el puerto 80 es accesible desde internet (ver HU-04.2 y HU-04.3).
- Si hay errores ACME: `kubectl describe challenge -A` muestra el detalle del challenge HTTP-01.
