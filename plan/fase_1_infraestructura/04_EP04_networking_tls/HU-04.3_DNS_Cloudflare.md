# HU-04.3 — DNS y Cloudflare

## Descripción General
Nuestra infraestructura ya está lista para recibir tráfico HTTPS válido. Sin embargo, no queremos exponer nuestro servidor Hetzner a ataques directos DDoS y el internet aún no sabe a qué IP apuntar si teclean `api.sereni.dad`. Utilizaremos Cloudflare como un escudo *Proxy* reverso inteligente, el cual pasará el tráfico encriptado, evaluará si es tráfico malicioso y luego viajará por el mundo hasta llegar a Traefik.

### ¿Qué se busca?
Asegurar TLS *Full Strict* de inicio a fin. Cloudflare proveerá su certificado gratis de borde a nuestros usuarios, y en el proceso de conexión contra nuestro VPS, exigirá validez criptográfica a nuestro controlador `cert-manager`.

---

## Ejecución Detallada

### T-04.3.1 — Apuntar Registros y Activar el Escudo Proxy
Interactuaremos con la API de Cloudflare usando Bash. Necesitas el `CF_API_TOKEN` y el `CF_ZONE_ID` definidos en tu archivo `.envrc` desde la fase 1.

```bash
# Cargar credenciales guardadas de forma local
source .envrc

# Ejecutar disparo al API de Cloudflare para crear registro tipo "A"
curl -s -X POST "https://api.cloudflare.com/client/v4/zones/${CF_ZONE_ID}/dns_records" \
  -H "Authorization: Bearer ${CF_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "A",
    "name": "api",
    "content": "'"${FLOATING_IP}"'",
    "ttl": 1,
    "proxied": true
  }' | yq '.' # Instalando yq (opcional) para leer el json mas amigable, o jq.

# Si esto retornó `success: true` procedes al paso de validación.

# Espera 1-2 minutos y revisa la resolución DNS usando los genéricos de Cloudflare.
# Deberia mostrar IPs de Cloudflare (ej. 104.21.x.x) y NO tu IP física Hetzner ($FLOATING_IP)
dig api.sereni.dad @1.1.1.1
```

### T-04.3.2 — Obligar uso de SSL Estricto y Política HSTS
Obligaremos a Cloudflare a no aceptar certificados autofirmados del origen (nuestro VPS) lo cual asegura la encriptación end-to-end, e inyectaremos los encabezados máximos de privacidad *HSTS*.

```bash
# Activar 'Full Strict'
curl -s -X PATCH "https://api.cloudflare.com/client/v4/zones/${CF_ZONE_ID}/settings/ssl" \
  -H "Authorization: Bearer ${CF_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"value":"strict"}'

# Habilitar HSTS (HTTP Strict Transport Security) durante todo un año a nivel Edge (Cloudflare)
curl -s -X PATCH "https://api.cloudflare.com/client/v4/zones/${CF_ZONE_ID}/settings/security_header" \
  -H "Authorization: Bearer ${CF_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "value": {
      "strict_transport_security": {
        "enabled": true,
        "max_age": 31536000,
        "include_subdomains": true,
        "nosniff": true,
        "preload": true
      }
    }
  }'
```

### T-04.3.3 — Verificación de Encriptación de Extremo a Extremo
El tráfico viaja: Cliente web -> Cloudflare (SSL Borde) -> Internet -> Traefik (SSL Origen) -> Aplicación.
Probemos mediante una evaluación externa en consola.

```bash
# 1. Hilar un simple Curl (Pide respuesta limpia libre de advertencias)
# Nuevamente un 404 es una excelente respuesta, porque es una respuesta del proxy interno validado.
curl -I https://api.sereni.dad

# 2. Investigar los headers del certificado digital
# Asegurarse que "s_client" nos reporta éxito (ver "Verify return code: 0 (ok)") y no nos bota a una excepción de certificación o auto-firma.
openssl s_client -connect api.sereni.dad:443 -servername api.sereni.dad </dev/null 2>/dev/null | grep -A 2 'Certificate chain'

# 3. Y el cabecero de privacidad:
curl -s -D- -o /dev/null https://api.sereni.dad | grep -i "strict-transport-security"
# Deberías ver: "strict-transport-security: max-age=31536000; includeSubdomains; preload"
```

Si todo responde eficientemente y los escudos demuestran estar arriba, la capa fundacional lógica SSL/Ingreso está **lista para interactuar**.
