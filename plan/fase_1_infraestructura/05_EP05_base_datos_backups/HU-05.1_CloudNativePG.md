# HU-05.1 — CloudNativePG y PostgreSQL 17.4

## Descripción General
Toda plataforma SaaS crítica necesita una capa de persistencia sólida. Elegimos PostgreSQL v17 por soporte nativo `UUIDv7` y usaremos el operador `CloudNativePG` para gobernarlo desde Kubernetes sin requerir DBA manual. Desplegaremos el operador, configuraremos un cluster de una sola instancia con recursos precisos para el hardware (Hetzner CX32), e inyectaremos la inicialización pre-programada (`postInitSQL`) que levantará las 6 bases de datos lógicas listas para los microservicios sin que los desarrolladores tengan qué crearlas.

### ¿Qué componentes tocamos?
1. **CloudNativePG Operator:** Es el software traductor que recibe comandos YAML y los convierte en comandos de administración DBA internos en un servidor Postgres.
2. **Cluster CRD (Custom Resource Definition):** El mapa de arquitectura de nuestro Postgres (memoria, discos NVMe, bases de datos base, extensiones). 
3. **Secretos SOPS:** Aprovisionamiento del santo grial (Contraseña de Administración).

## Ejecución Detallada

### T-05.1.1 — Declarar el Repositorio de CloudNativePG
Definiremos de dónde Flux extraerá los manifiestos oficiales de CloudNative.

```bash
# Navegar a la raíz del monorepo
cat <<EOF > infra/infrastructure/cnpg/helmrepository.yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: HelmRepository
metadata:
  name: cnpg
  namespace: flux-system
spec:
  interval: 1h
  url: https://cloudnative-pg.github.io/charts
EOF
```

### T-05.1.2 — Lanzar el Operador CNPG
Configuraremos el archivo `HelmRelease`. No estamos levantando Postgres todavía, sino el *software que administra* Postgres.

```bash
cat <<EOF > infra/infrastructure/cnpg/helmrelease.yaml
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: cnpg
  namespace: cnpg-system
spec:
  interval: 10m
  chart:
    spec:
      chart: cloudnative-pg
      version: '>=0.22.0'
      sourceRef:
        kind: HelmRepository
        name: cnpg
        namespace: flux-system
  install:
    createNamespace: true
  values:
    monitoring:
      podMonitorEnabled: false # En fase 3 encenderemos Prometheus
    resources:
      requests:
        cpu: 20m
        memory: 64Mi
      limits:
        cpu: 200m
        memory: 128Mi
EOF
```

### T-05.1.3 — Generación y Cifrado de Credencial Administradora
Generaremos la contraseña `superuser` y la cifraremos utilizando la utilidad SOPS creada en el sprint previo. ¡Solo en tu máquina quedará rastro limpio! 

```bash
# Nos movemos a la raíz asegurándonos que el script encrypt-secret vea el archivo de reglas SOPS local
# Generamos password fuerte usando OpenSSL
export PG_ADMIN_PASSWORD=$(openssl rand -base64 32)
echo "TU CONTRASEÑA ADMIN GLOBAL A GUARDAR EN BITWARDEN/1PASSWORD ES: ${PG_ADMIN_PASSWORD}"

# Ejecutamos nuestra utilidad creada en HU-03.3
# OJO: Se almacena en el namespace "serenidad-data" que será dueña de la DB
./scripts/encrypt-secret.sh serenidad-data cnpg-serenidad-admin-creds \
  username=serenidad_admin \
  password=${PG_ADMIN_PASSWORD}

# Limpiamos rastros en consola local por seguridad
unset PG_ADMIN_PASSWORD
```

### T-05.1.4 — Orquestar el Motor PostgreSQL y las Reglas de Negocio
Crearemos la configuración "física" virtual de la BD. Asignaremos 20GB al disco, y daremos un ajuste estricto al 25% de la RAM real de tu servidor Hetzner (CX32 = 8GB RAM). 

El `postInitSQL` contiene el "arranque de fábrica". Apenas prenda el motor y la red, PG creará las bases e instalará extensiones GIS (`btree_gist`) y de monitoreo (`pg_stat_statements`).

```bash
cat <<EOF > infra/infrastructure/cnpg/cluster.yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: serenidad-pg
  namespace: serenidad-data
spec:
  instances: 1
  imageName: ghcr.io/cloudnative-pg/postgresql:17.4
  enablePodMonitor: false
  
  # Calibración FINA para servidor Hetzner CX32 (8GB RAM, discos NVMe)
  postgresql:
    shared_preload_libraries:
      - "pg_stat_statements"
    parameters:
      shared_buffers: "512MB"
      effective_cache_size: "1536MB"
      maintenance_work_mem: "128MB"
      work_mem: "16MB"
      max_connections: "100"
      wal_buffers: "16MB"
      checkpoint_completion_target: "0.9"
      random_page_cost: "1.1"               # Asumiendo Local-Path en SSD NVMe de Hetzner
      effective_io_concurrency: "200"
      min_wal_size: "256MB"
      max_wal_size: "2GB"
      log_min_duration_statement: "1000"    # Loggea queries más lentas de 1s
      log_checkpoints: "on"
      log_lock_waits: "on"
      
  # Sembrado Mágico en el Arranque 0
  bootstrap:
    initdb:
      database: admin_db # Base default root
      owner: serenidad_admin
      secret:
        name: cnpg-serenidad-admin-creds
      postInitSQL:
        - "CREATE DATABASE iam_db OWNER serenidad_admin ENCODING 'UTF8' LC_COLLATE 'C';"
        - "CREATE DATABASE kratos_db OWNER serenidad_admin ENCODING 'UTF8' LC_COLLATE 'C';"
        - "CREATE DATABASE openfga_db OWNER serenidad_admin ENCODING 'UTF8' LC_COLLATE 'C';"
        - "CREATE DATABASE scheduling_db OWNER serenidad_admin ENCODING 'UTF8' LC_COLLATE 'C';"
        - "CREATE DATABASE clinical_db OWNER serenidad_admin ENCODING 'UTF8' LC_COLLATE 'C';"
        - "CREATE DATABASE billing_db OWNER serenidad_admin ENCODING 'UTF8' LC_COLLATE 'C';"
        # Entramos a cada base de microservicio e instalamos la extensión de observabilidad y las espaciales
        - "\c iam_db"
        - "CREATE EXTENSION IF NOT EXISTS pg_stat_statements;"
        - "CREATE EXTENSION IF NOT EXISTS btree_gist;"
        - "\c scheduling_db"
        - "CREATE EXTENSION IF NOT EXISTS pg_stat_statements;"
        - "CREATE EXTENSION IF NOT EXISTS btree_gist;"
        - "\c clinical_db"
        - "CREATE EXTENSION IF NOT EXISTS pg_stat_statements;"
        - "\c billing_db"
        - "CREATE EXTENSION IF NOT EXISTS pg_stat_statements;"

  # Configuración de Servidor de Respaldo B2
  backup:
    barmanObjectStore:
      # Placeholder: Los secretos seran inyectados despues en HU-05.2
      destinationPath: "s3://serenidad-pg-backups/wal"
      endpointURL: "https://s3.us-east-005.backblazeb2.com" # CAMBIAR POR TU REGIÓN B2!!
      s3Credentials:
        accessKeyId:
          name: cnpg-b2-credentials
          key: B2_KEY_ID
        secretAccessKey:
          name: cnpg-b2-credentials
          key: B2_APPLICATION_KEY
      wal:
        compression: gzip
        maxParallel: 2
      data:
        compression: gzip
        jobs: 2
    retentionPolicy: "30d"

  # Disco persistente Local SSD
  storage:
    size: 20Gi
    storageClass: local-path
    
  # Recursos del Pod
  resources:
    requests:
      cpu: "100m"
      memory: "256Mi"
    limits:
      cpu: "1000m"
      memory: "512Mi"
EOF

# Advertencia analista: Asegúrate de reemplazar "https://s3.us-east-005..." en el endpoint si Backblaze te asignó otro "S3 Endpoint" diferente durante T-01.1.4.
```

### T-05.1.5 — Configurar Índices GitOps y Empujar Cambios
Completamos el archivo kustomization integrando secretos provisoriamente, el helmrelease y el Cluster para inyectar todo en cadena.

```bash
cat <<EOF > infra/infrastructure/cnpg/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: serenidad-data

resources:
  - helmrepository.yaml
  - helmrelease.yaml
  - cluster.yaml
  # Las llaves a continuacion las hemos guardado en SOPS. Kustomize las incluirá virtualmente.
  - ../../secrets/cnpg-serenidad-admin-creds.yaml
EOF

git add infra/infrastructure/cnpg/ infra/secrets/cnpg-serenidad-admin-creds.yaml
git commit -m "feat(database): deploy CloudNativePG operator and central postgres cluster"
git push origin main
flux reconcile kustomization flux-system --with-source
```

### T-05.1.6 — Pruebas de Integridad
Verificaremos a fondo que la base de datos se desplegó y responde al usuario.
Esta tarea debe ejecutarse tras unos 3-5 minutos cuando descargue la imagen Docker.

```bash
# 1. Esperamos salud del nodo (debe reportar 'Cluster in healthy state').
kubectl get cluster serenidad-pg -n serenidad-data
kubectl wait cluster serenidad-pg --for=condition=Ready -n serenidad-data --timeout=300s

# 2. Revisa que CNPG ha exportado credenciales automáticamente
kubectl get secrets -n serenidad-data | grep cnpg

# 3. Prueba Máxima: Meterse en un terminal dentro del servidor BD como administrador y listar bases ' \l '. 
# Observaremos 'iam_db', 'kratos_db', etc...
kubectl exec -it serenidad-pg-1 -n serenidad-data -- psql -U serenidad_admin -c "\l"

# 4. Validar soporte al algoritmo de IDs modernos UUIDv7 que Kratos exigirá (nativo en PG17)
kubectl exec -it serenidad-pg-1 -n serenidad-data -- psql -U serenidad_admin -c "SELECT gen_random_uuid()::text"

# 5. Si eres purista/analista de datos, confirma tu asignación RAM NVMe:
kubectl exec -it serenidad-pg-1 -n serenidad-data -- psql -U serenidad_admin -c "SHOW shared_buffers" # Debe ser 512MB
```
