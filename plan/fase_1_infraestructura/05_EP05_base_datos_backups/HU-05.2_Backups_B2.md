# HU-05.2 — Copias de Seguridad: B2 y WAL Archiving Continúo

## Descripción General
Tierra de desastres. Un disco NVMe se corrompe o alguien tira un comando `DROP TABLE`. ¿Qué hacemos?
PostgreSQL no guarda la data al instante, guarda cada mínima acción en los archivos WAL (Write-Ahead-Log). En esta historia, enlazaremos nuestro *Bucket* de Backblaze B2 al Clúster PG. CNPG ejecutará un enrutado en tiempo real subiendo cada WAL nuevo (PITR Point-in-Time-Recovery; capacidad de regresar al segundo exacto de vida previa) y programará una inyección pesada 1 vez al día de 100% de la información cruda para retenciones a largo plazo.

### Componentes Involucrados:
1. **Secretos CNPG B2:** Autenticación S3 nativa.
2. **ScheduledBackups CRD:** Cronjobs orquestados por el operador para tirar fotos masivas al Bucket cada madrugada.

## Ejecución Detallada

### T-05.2.1 — Cifrar y Transmitir Credenciales S3
Tal como generamos credenciales de Admin en la *HU-05.1*, inyectaremos al sistema los tokens proveídos por Backblaze creados en la Fase de Cuentas (F1E01).

```bash
# Exportar las credencias como variable temporal asumiendo las tienes ya guardadas.
# Sustitutelas o cárgalas en el comando abajo:
B2_KEY_ID="tu-verdadero-key-id"
B2_APPLICATION_KEY="tu-verdadero-application-key-crudo"

# Instanciamos el secret via SOPS para no exponerlo al repositorio GitHub/GitLab
./scripts/encrypt-secret.sh serenidad-data cnpg-b2-credentials \
  B2_KEY_ID=${B2_KEY_ID} \
  B2_APPLICATION_KEY=${B2_APPLICATION_KEY}

# Borrar rastro shell local
unset B2_KEY_ID
unset B2_APPLICATION_KEY

# Anclar y empujar a Git
git add infra/secrets/cnpg-b2-credentials.yaml
git commit -m "feat(security): provide encrypted B2 credentials for wal archiving"
git push origin main
flux reconcile kustomization flux-system --with-source

# En este momento, Kustomize añade el secreto, CloudNativePG lo empareja con la configuración WAL 
# de la BD (creada en la HU pasada) y de inmediato comenzará a empujar los logs en vivo.
```

### T-05.2.2 — Validar el Motor en Tiempo Real (WAL Archiver)
Cercioremos que Barman (herramienta que reside en el pod que empaqueta las copias de seguridad de BD) es capaz de comunicarse tras la entrega de nuestra llave.

```bash
# Analiza los sublogs vitales buscando la validación de barman. 
# Si tu credencial B2 falló, verás avisos como 'failed to assume S3 role' o 'connection refused'. 
kubectl logs serenidad-pg-1 -n serenidad-data | grep -i -E "wal|archive|barman|s3"

# En el terminal, si instalaste el cli b2 localmente o usando panel web visual B2 Backblaze,
# Entra al Bucket "serenidad-pg-backups" -> y podrás notar que dentro de "wal/wals/"
# empiezan a brotar archivos de 16MB. ¡Magia!
```

### T-05.2.3 — Programar Respaldo Profundo Diario (ScheduledBackup)
Ahora que los pequeños fragmentos se salvan, requerimos crear CRD que guarde una foto entera cada madrugada (Tarda más e impacta IOPS, un `pg_basebackup` esencialmente).

```bash
# Definimos cronjob de backup vía CRD apuntando al cluster 02:00 UTC
cat <<EOF > infra/infrastructure/cnpg/scheduled-backup.yaml
apiVersion: postgresql.cnpg.io/v1
kind: ScheduledBackup
metadata:
  name: serenidad-pg-daily
  namespace: serenidad-data
spec:
  schedule: "0 2 * * *"
  backupOwnerReference: self
  immediate: true       # Obliga a disparar AHORA el primer Snapshot Base apenas exista este archivo.
  cluster:
    name: serenidad-pg
EOF

# Lo insertamos en el índice local
cat <<EOF >> infra/infrastructure/cnpg/kustomization.yaml
  - scheduled-backup.yaml
  - ../../secrets/cnpg-b2-credentials.yaml
EOF

git add infra/infrastructure/cnpg/
git commit -m "feat(database): configure daily snapshot backups to external S3 object store"
git push origin main
flux reconcile kustomization flux-system --with-source
```

### T-05.2.4 — Auditoría de Ejecución de la Foto Inicial
Debido a nuestro `immediate: true`, el servidor ya debe estar compilando el resguardo base y mandándolo a la red mundial.

```bash
# 1. Checar el estatus de la operación, hasta que arroje Phase "Completed"
kubectl get backup -n serenidad-data
# Si arroja Running esperar unos momentos, si arroja Failed, auditar con 'kubectl describe backup'

# 2. Cuando veas Completado, verificar en el panel Backblaze Web Console:
# "serenidad-pg-backups" -> En "wal/base" ahora se encuentra tu foto gruesa empaquetada `.tar.gz`.

# PITR es ahora posible. El sistema mantendrá limpios y borrará backups base que superen
# nuestra regla maestra 'retentionPolicy: 30d' del Cluster original.
```
