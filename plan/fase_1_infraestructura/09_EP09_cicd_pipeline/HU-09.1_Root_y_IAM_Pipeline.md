# HU-09.1 (Parte A) — Orquestador Raíz y Pipeline del IAM Service

## Descripción General

El pipeline de CI/CD es el mecanismo que transforma cada `git push` a `main` en un despliegue reproducible y auditado, sin intervención manual. La estrategia se basa en un **modelo monorepo modular** con dos fases diferenciadas:

1. **Orquestador raíz** (`.gitlab-ci.yml`): Detecta qué componente cambió e incluye únicamente el sub-pipeline correspondiente, evitando ejecuciones innecesarias.
2. **Sub-pipelines especializados** (`.gitlab/ci/*.yml`): Cada componente define su propio flujo de `test → build → deploy`.

### Modelo de despliegue del IAM Service (GitOps pull)

El IAM Service sigue un modelo **pull-based** mediante FluxCD:

```
git push → GitLab CI → docker build + push → registry.gitlab.com
                     ↓
              sed: actualiza imagen en infra/apps/iam-service/deployment.yaml
                     ↓
              git push [skip ci] → rama main
                     ↓
              FluxCD detecta cambio → kubectl apply → Kubernetes
```

FluxCD nunca recibe órdenes directas desde CI; en cambio, observa el repositorio y reconcilia automáticamente el estado deseado.

### Compatibilidad de imágenes

| Componente | Imagen base | Justificación |
|---|---|---|
| `test-iam` | `golang:1.25-alpine` | Alpine minimiza el tiempo de descarga; Go 1.25 es el runtime objetivo |
| `build-push-iam` | `docker:26` + `docker:26-dind` | Docker-in-Docker para construir la imagen Distroless |
| IAM Service final | `gcr.io/distroless/static-debian12` | Sin shell ni herramientas; superficie de ataque mínima |

## Ejecución Detallada

### T-09.1.1 — Crear el orquestador raíz `.gitlab-ci.yml`

```bash
# Ejecutar desde la raíz del monorepo
mkdir -p .gitlab/ci

cat > .gitlab-ci.yml << 'EOF'
# =============================================================================
# Orquestador raíz del monorepo serenidad-platform
# Cada include se activa selectivamente según los archivos modificados.
# Los sub-pipelines llevan sus propias reglas de activación (rules.changes).
# =============================================================================

stages:
  - test
  - build
  - deploy

variables:
  # Versiones fijadas para reproducibilidad
  GO_VERSION: "1.25"
  DOCKER_VERSION: "26"
  BUN_VERSION: "1.3"
  NODE_IMAGE: "node:22-alpine"

# Incluir sub-pipelines. GitLab los carga en el pipeline solo cuando
# las reglas internas de cada archivo se cumplen.
include:
  - local: .gitlab/ci/iam-service.yml
  - local: .gitlab/ci/deploy-bff.yml
  - local: .gitlab/ci/deploy-web.yml
EOF
```

### T-09.1.2 — Pipeline del IAM Service: test y build

El pipeline del IAM Service cubre dos trabajos:

- **`test-iam`**: Ejecutado en merge requests y pushes a `main` que toquen `services/iam/`. Corre `go vet`, `go test -race` y reporta la cobertura.
- **`build-push-iam`**: Solo en `main`. Construye la imagen Distroless, la sube al GitLab Container Registry y actualiza el tag en el manifiesto de Kustomize vía `git push [skip ci]`.

```bash
cat > .gitlab/ci/iam-service.yml << 'EOF'
# =============================================================================
# Pipeline del IAM Domain Service (Go 1.25)
# =============================================================================

# ── Test ──────────────────────────────────────────────────────────────────────
test-iam:
  stage: test
  image: golang:${GO_VERSION}-alpine
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      changes:
        - services/iam/**/*
        - .gitlab/ci/iam-service.yml
    - if: $CI_COMMIT_BRANCH == "main"
      changes:
        - services/iam/**/*
        - .gitlab/ci/iam-service.yml
  cache:
    key: go-mod-$CI_COMMIT_REF_SLUG
    paths:
      - /go/pkg/mod/
  before_script:
    - apk add --no-cache gcc musl-dev  # necesario para go test -race en Alpine
  script:
    - cd services/iam
    - go mod download
    - go vet ./...
    - go test -v -race -coverprofile=coverage.out -covermode=atomic ./...
    - go tool cover -func=coverage.out | tail -1
  coverage: '/total:\s+\(statements\)\s+(\d+\.\d+)%/'
  artifacts:
    reports:
      coverage_report:
        coverage_format: cobertura
        path: services/iam/coverage.xml
    paths:
      - services/iam/coverage.out
    expire_in: 1 week

# ── Build y GitOps update ─────────────────────────────────────────────────────
build-push-iam:
  stage: build
  image: docker:${DOCKER_VERSION}
  services:
    - docker:${DOCKER_VERSION}-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
    IMAGE: $CI_REGISTRY_IMAGE/iam-service
    MANIFEST: infra/apps/iam-service/deployment.yaml
  needs:
    - job: test-iam
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      changes:
        - services/iam/**/*
        - .gitlab/ci/iam-service.yml
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - apk add --no-cache git
  script:
    # ── 1. Build de la imagen Distroless ──────────────────────────────────────
    - |
      docker build \
        --build-arg GO_VERSION=${GO_VERSION} \
        --tag "${IMAGE}:${CI_COMMIT_SHORT_SHA}" \
        --tag "${IMAGE}:latest" \
        --file services/iam/Dockerfile \
        services/iam/

    # ── 2. Push al GitLab Container Registry ─────────────────────────────────
    - docker push "${IMAGE}:${CI_COMMIT_SHORT_SHA}"
    - docker push "${IMAGE}:latest"

    # ── 3. Mutación GitOps: actualizar el tag en el manifiesto ───────────────
    # Este paso hace que FluxCD detecte el nuevo SHA y reconcilie el cluster.
    - git config user.email "gitlab-ci@sereni.dad"
    - git config user.name "GitLab CI Bot"
    - git remote set-url origin "https://oauth2:${CI_JOB_TOKEN}@${CI_SERVER_HOST}/${CI_PROJECT_PATH}.git"
    - git fetch origin main
    - git checkout main
    - git pull origin main

    # Reemplazar el tag de imagen en el Deployment de Kustomize
    # El manifiesto debe tener la línea: image: registry.gitlab.com/.../iam-service:SHA
    - |
      sed -i \
        "s|image: ${IMAGE}:.*|image: ${IMAGE}:${CI_COMMIT_SHORT_SHA}|g" \
        "${MANIFEST}"

    # Verificar que el sed encontró y modificó la línea
    - grep "image: ${IMAGE}:${CI_COMMIT_SHORT_SHA}" "${MANIFEST}"

    - git add "${MANIFEST}"
    - |
      git commit -m "chore(gitops): bump iam-service to ${CI_COMMIT_SHORT_SHA} [skip ci]"
    - git push origin HEAD:main
EOF
```

**Nota sobre `[skip ci]`:** El mensaje `[skip ci]` en el commit del bot instruye a GitLab a no ejecutar otro pipeline para ese commit, evitando bucles infinitos.

### T-09.1.3 — Estructura esperada del Deployment de Kustomize

El manifiesto `infra/apps/iam-service/deployment.yaml` debe contener una línea de imagen con el formato exacto que `sed` buscará:

```yaml
# infra/apps/iam-service/deployment.yaml (fragmento relevante)
spec:
  template:
    spec:
      containers:
        - name: iam-service
          # Esta línea es mutada automáticamente por el pipeline
          image: registry.gitlab.com/serenidad/serenidad-platform/iam-service:INITIAL_SHA
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 30
```

### T-09.1.4 — Configurar variables CI/CD en GitLab

Las variables predefinidas de GitLab (`CI_REGISTRY_*`, `CI_COMMIT_SHORT_SHA`, `CI_JOB_TOKEN`) se inyectan automáticamente. Solo deben configurarse manualmente las variables externas:

```bash
# Usando glab CLI (autenticado previamente en HU-01.4)
# No requiere configuración adicional para el pipeline del IAM Service:
# - CI_REGISTRY, CI_REGISTRY_USER, CI_REGISTRY_PASSWORD: automáticas
# - CI_JOB_TOKEN: efímero por pipeline, generado automáticamente

# Para verificar que el Container Registry está habilitado en el proyecto:
glab api projects/$CI_PROJECT_ID | jq '.container_registry_enabled'
# Debe retornar: true
```

### T-09.1.5 — Commit y activación del pipeline

```bash
# Agregar los archivos del pipeline al repositorio
git add .gitlab-ci.yml .gitlab/ci/iam-service.yml

git commit -m "feat(ci): add root orchestrator and IAM service CI/CD pipeline with GitOps image update"
git push origin main
```

**Verificar en GitLab UI:**

```
Repositorio → Build → Pipelines → Pipeline más reciente
```

El primer push activa el pipeline solo si `services/iam/` o `.gitlab/ci/iam-service.yml` cambiaron. Para forzar una prueba:

```bash
# Tocar un archivo inofensivo en services/iam/ para disparar el pipeline
echo "# build trigger $(date -u +%Y%m%dT%H%M%SZ)" >> services/iam/README.md
git add services/iam/README.md
git commit -m "test(ci): trigger iam pipeline to verify automation"
git push origin main
```

### T-09.1.6 — Verificar el despliegue end-to-end

Una vez que el pipeline completa (≈ 5 minutos), FluxCD detecta el cambio en el manifiesto y lo aplica (≈ 1-3 minutos adicionales):

```bash
# 1. Verificar que el pipeline de GitLab completó sin errores
glab ci view  # Muestra el estado del último pipeline en la terminal

# 2. Observar la reconciliación de FluxCD
flux get kustomization serenidad-apps -n flux-system --watch
# La columna "READY" pasará a "True" cuando el nuevo SHA esté aplicado

# 3. Verificar que el Deployment en K8s tiene la nueva imagen
kubectl get deployment iam-service -n serenidad-core \
  -o jsonpath='{.spec.template.spec.containers[0].image}'
# Debe mostrar: registry.gitlab.com/.../iam-service:<CI_COMMIT_SHORT_SHA>

# 4. Verificar que el Pod nuevo está en Running con la imagen actualizada
kubectl rollout status deployment/iam-service -n serenidad-core --timeout=120s
# "deployment "iam-service" successfully rolled out"

# 5. Verificar health del servicio
curl -s https://api.sereni.dad/api/iam/health
# {"status":"ok","service":"iam-service","version":"<SHA>"}
```

| CA-09.1.1 | Pipeline solo se activa cuando `services/iam/` o `.gitlab/ci/iam-service.yml` cambian | Push a `README.md` raíz → no dispara `test-iam` ni `build-push-iam` |
