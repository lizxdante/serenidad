# HU-09.1 (Parte A): Orquestador y Pipeline del IAM Service

## Descripción General
Para alcanzar el nivel de *Continuous Deployment* real y evitar humanos lanzando comandos `wrangler` o `docker push` de forma local, le delegaremos el trabajo a **GitLab CI/CD**.
Configuraremos un modelo monorepo modular: existirá un archivo orquestador base en la raíz de nuestro proyecto, el cual delegará de acuerdo a la carpeta modificada a sub-pipelines especializados.

En este manual crearemos la raíz y el proceso automatizado del microservicio central (IAM Service), logrando desplegar su testeo estricto en Go, la compilación `Distroless` y su reconciliación con *FluxCD* (GitOps).

---

## Ejecución Detallada

### T-09.1.1 — Instanciar la Orquestación de CI/CD
El manifiesto principal del que GitLab aprenderá qué rutas activar según nuestras modificaciones.

```bash
# Estando en la rama 'main' del monorepo
mkdir -p .gitlab/ci/

cat <<EOF > .gitlab-ci.yml
# Raíz Integradora de Pipelines de Serenidad
stages:
  - test
  - build
  - deploy

include:
  - local: .gitlab/ci/iam-service.yml
  - local: .gitlab/ci/deploy-bff.yml
  - local: .gitlab/ci/deploy-web.yml
EOF
```

### T-09.1.2 — Pipeline de Integración y Entrega (CI/CD) para el Backend Go
Construiremos un flujo de dos etapas (Testeo y Construcción/Entrega). 
La segunda etapa hará una técnica nativa de GitOps: Usará un contenedor Docker in-runner temporal para compilar, conectarse al Registry de GitLab, subir la imagen y acto seguido hará uso del bash para ubicar el manifiesto de Kustomize y cambiar el SHA (versión de nuestra imagen). Esto obligará a *FluxCD* a enterarse de una actualización y jalar los cambios al clúster sin que GitLab se comunique directamente con el servidor físico.

```bash
cat <<'EOF' > .gitlab/ci/iam-service.yml
variables:
  GO_VERSION: "1.25"

test-iam:
  stage: test
  image: golang:${GO_VERSION}-alpine
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      changes:
        - services/iam/**/*
    - if: $CI_COMMIT_BRANCH == "main"
      changes:
        - services/iam/**/*
        - .gitlab/ci/iam-service.yml
  cache:
    key: go-mod-${CI_COMMIT_REF_SLUG}
    paths:
      - vendor/
      - /go/pkg/mod/
  script:
    - cd services/iam
    - go mod download
    - go vet ./...
    - go test -v -race -coverprofile=coverage.out ./...
    - go tool cover -func=coverage.out
  coverage: '/total:\s+\(statements\)\s+(\d+\.\d+)%/'

build-push-iam:
  stage: build
  image: docker:26
  services:
    - docker:26-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  needs: ["test-iam"]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      changes:
        - services/iam/**/*
        - .gitlab/ci/iam-service.yml
  before_script:
    # Autenticación automática de runners
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - apk add --no-cache git
  script:
    # 1. Build and push de nueva version al Container Registry
    - docker build -t ${CI_REGISTRY_IMAGE}/iam-service:${CI_COMMIT_SHORT_SHA} -t ${CI_REGISTRY_IMAGE}/iam-service:latest -f services/iam/Dockerfile services/iam/
    - docker push ${CI_REGISTRY_IMAGE}/iam-service:${CI_COMMIT_SHORT_SHA}
    - docker push ${CI_REGISTRY_IMAGE}/iam-service:latest
    # 2. Mutación de infraestructura GitOps 
    - git config --global user.email "gitlab-ci@sereni.dad"
    - git config --global user.name "Gitlab CI/CD Bot"
    - git checkout main
    - git pull origin main
    - sed -i "s|image: ${CI_REGISTRY_IMAGE}/iam-service:.*|image: ${CI_REGISTRY_IMAGE}/iam-service:${CI_COMMIT_SHORT_SHA}|" infra/apps/iam-service/deployment.yaml
    - git commit -am "chore(gitops): auto-update iam-service to ${CI_COMMIT_SHORT_SHA} [skip ci]"
    # Usar Job Token dinámico para pushear la version superando las politicas protectivas
    - git push https://oauth2:${CI_JOB_TOKEN}@${CI_SERVER_HOST}/${CI_PROJECT_PATH}.git HEAD:main
EOF
```

### T-09.1.5 — Verificar Despliegue del Sistema Central
Si el push se ejecuta con éxito, este proceso demorará unos tres a cinco minutos la primera vez.

1. **Observar en GitLab CI:** Haz commit sobre algún archivo inofensivo de `/services/iam` (ej: un readme o un comentario go). Ir a `Build -> Pipelines`.
2. Verás al linter y los test del coverage reportar.
3. Si son superados, la rama `main` de tu repositorio recibirá un PUSH silencioso desde el BOT.
4. Conéctate por terminal a tu Kubernetes y ejecuta:
```bash
flux get all
# Tras 1 min, flux notará el cambio del BOT y aplicará la nueva revisión sin fallos.
```
