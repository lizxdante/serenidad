# HU-09.1 (Parte B) — Pipelines del Edge: BFF y SPA Web

## Descripción General

Los componentes de edge (BFF en Cloudflare Workers y SPA en Cloudflare Pages) siguen un modelo de despliegue **push-based**, a diferencia del IAM Service que usa el modelo pull de FluxCD. Esta diferencia es arquitecturalmente intencional:

| Componente | Modelo | Razón |
|---|---|---|
| IAM Service (Go/K8s) | Pull (FluxCD) | Estado declarativo en Git; FluxCD gestiona reconciliación |
| BFF (Cloudflare Workers) | Push (wrangler deploy) | Sin estado en cluster; Cloudflare gestiona el runtime |
| SPA Web (Cloudflare Pages) | Push (wrangler pages deploy) | Assets estáticos + SSR edge; Cloudflare gestiona CDN |

```
git push → GitLab CI → wrangler deploy → Cloudflare Workers/Pages
                   ↑
         (autenticado con CLOUDFLARE_API_TOKEN)
```

Cloudflare propaga el deployment globalmente en menos de 30 segundos.

### Variables CI/CD requeridas en GitLab

Antes de ejecutar estos pipelines, las siguientes variables deben estar configuradas en `Settings → CI/CD → Variables` del proyecto GitLab, con el atributo **Protected** habilitado:

| Variable | Tipo | Descripción |
|---|---|---|
| `CF_API_TOKEN` | Secret (masked) | Token de Cloudflare con permisos `Workers Scripts:Edit`, `Pages:Edit` |
| `CF_ACCOUNT_ID` | Variable | Account ID de Cloudflare (visible en el dashboard) |

```bash
# Configurar via glab CLI (requiere autenticación previa)
glab variable set CF_API_TOKEN --value "<token>" --masked --protected
glab variable set CF_ACCOUNT_ID --value "<account_id>" --protected
```

## Ejecución Detallada

### T-09.1.3 — Pipeline de deploy del BFF a Cloudflare Workers

El BFF usa `bun` como package manager y runtime, y `wrangler` para el deploy. El pipeline verifica los tipos TypeScript antes de cada deploy.

```bash
cat > .gitlab/ci/deploy-bff.yml << 'EOF'
# =============================================================================
# Pipeline del BFF — Hono v4 en Cloudflare Workers
# Modelo: Push directo via wrangler
# =============================================================================

deploy-bff:
  stage: deploy
  image: node:22-alpine
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      changes:
        - apps/bff/**/*
        - .gitlab/ci/deploy-bff.yml
  variables:
    # Credenciales de Cloudflare (referenciadas desde las variables CI/CD del proyecto)
    CLOUDFLARE_API_TOKEN: $CF_API_TOKEN
    CLOUDFLARE_ACCOUNT_ID: $CF_ACCOUNT_ID
  before_script:
    # Instalar bun y wrangler una sola vez en el runner
    - npm install -g bun@latest wrangler@latest --silent
    - cd apps/bff
    - bun install --frozen-lockfile
  script:
    # ── 1. Verificación de tipos TypeScript ───────────────────────────────────
    # verbatimModuleSyntax: true — cualquier import de tipo sin 'import type'
    # causa error de compilación aquí, antes de llegar a producción.
    - bun run tsc --noEmit
    # Debe completar sin output (0 errores)

    # ── 2. Deploy a Cloudflare Workers ────────────────────────────────────────
    # wrangler lee wrangler.toml en apps/bff/ para la configuración del Worker
    - wrangler deploy --minify

    # ── 3. Verificar que el Worker responde ───────────────────────────────────
    - |
      sleep 10  # Dar tiempo a Cloudflare para propagar el deployment
      STATUS=$(curl -s -o /dev/null -w "%{http_code}" https://api.sereni.dad/bff/health)
      if [ "$STATUS" != "200" ]; then
        echo "ERROR: Health check falló con HTTP ${STATUS}"
        exit 1
      fi
      echo "OK: BFF health check retornó HTTP 200"
EOF
```

### T-09.1.4 — Pipeline de deploy de la SPA Qwik a Cloudflare Pages

La SPA requiere pasar las variables de entorno de build al proceso de Vite. Estas variables se inyectan como variables de entorno en el job y Vite las expone al código del cliente mediante el prefijo `VITE_`.

```bash
cat > .gitlab/ci/deploy-web.yml << 'EOF'
# =============================================================================
# Pipeline de la SPA Qwik v2 — Cloudflare Pages
# Modelo: Push via wrangler pages deploy
# =============================================================================

deploy-web:
  stage: deploy
  image: node:22-alpine
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      changes:
        - apps/web/**/*
        - .gitlab/ci/deploy-web.yml
  variables:
    # Credenciales de Cloudflare
    CLOUDFLARE_API_TOKEN: $CF_API_TOKEN
    CLOUDFLARE_ACCOUNT_ID: $CF_ACCOUNT_ID
    # Variables de build inyectadas por Vite durante `bun run build`
    # Accesibles en el código como import.meta.env.VITE_API_BASE_URL
    VITE_API_BASE_URL: "https://api.sereni.dad/bff"
    VITE_KRATOS_URL: "https://api.sereni.dad/auth"
  before_script:
    - npm install -g bun@latest wrangler@latest --silent
    - cd apps/web
    - bun install --frozen-lockfile
  script:
    # ── 1. Build de producción con Qwik v2 + Vite ────────────────────────────
    # El adaptador de Cloudflare Pages genera:
    #   dist/ — assets estáticos
    #   dist/_worker.js — SSR edge function
    - bun run build

    # ── 2. Verificar que el build generó los assets esperados ─────────────────
    - |
      if [ ! -f "dist/_worker.js" ]; then
        echo "ERROR: dist/_worker.js no encontrado. El build del adaptador CF Pages falló."
        exit 1
      fi
      echo "Build OK — assets generados:"
      du -sh dist/

    # ── 3. Deploy a Cloudflare Pages ──────────────────────────────────────────
    - |
      wrangler pages deploy dist/ \
        --project-name serenidad-web \
        --branch main \
        --commit-hash "${CI_COMMIT_SHORT_SHA}"

    # ── 4. Verificar que la SPA responde con HTML válido ─────────────────────
    - |
      sleep 15  # Cloudflare Pages propaga en ~10-30 segundos
      CONTENT_TYPE=$(curl -sI https://app.sereni.dad | grep -i content-type | head -1)
      if echo "$CONTENT_TYPE" | grep -qi "text/html"; then
        echo "OK: SPA retorna HTML"
      else
        echo "ERROR: Content-Type inesperado: ${CONTENT_TYPE}"
        exit 1
      fi
EOF
```

### T-09.1.6 — Verificar la activación selectiva

La activación selectiva es el mecanismo clave para no desperdiciar minutos de CI/CD en cambios no relacionados:

```bash
# ── Prueba 1: Cambio irrelevante — no debe disparar ningún pipeline edge ──────
echo "# irrelevant change" >> docs/architecture.md
git add docs/architecture.md
git commit -m "docs: minor update to architecture notes"
git push origin main
# Resultado esperado: GitLab muestra el pipeline pero ningún job de deploy-bff
# ni deploy-web se ejecuta (skipped por rules.changes)

# ── Prueba 2: Cambio solo en BFF — solo deploy-bff debe ejecutarse ────────────
echo "// touch" >> apps/bff/src/index.ts
git add apps/bff/src/index.ts
git commit -m "test(ci): verify selective BFF pipeline activation"
git push origin main
# Resultado esperado: solo deploy-bff se ejecuta; deploy-web y test-iam quedan en "skipped"

# ── Prueba 3: Cambio solo en Web — solo deploy-web debe ejecutarse ─────────────
echo "// touch" >> apps/web/src/routes/index.tsx
git add apps/web/src/routes/index.tsx
git commit -m "test(ci): verify selective Web pipeline activation"
git push origin main
# Resultado esperado: solo deploy-web se ejecuta
```

### T-09.1.7 — Diccionario de variables automáticas de GitLab CI

Las siguientes variables son inyectadas por GitLab en cada runner. No requieren configuración manual:

| Variable | Valor de ejemplo | Propósito en los pipelines |
|---|---|---|
| `$CI_REGISTRY` | `registry.gitlab.com` | Host del Container Registry integrado de GitLab |
| `$CI_REGISTRY_USER` | `gitlab-ci-token` | Usuario sintético y efímero para docker login |
| `$CI_REGISTRY_PASSWORD` | `<token efímero>` | Contraseña del usuario anterior; expira al terminar el pipeline |
| `$CI_REGISTRY_IMAGE` | `registry.gitlab.com/serenidad/serenidad-platform` | Namespace de imágenes del proyecto |
| `$CI_COMMIT_SHORT_SHA` | `a1b2c3d4` | Primeros 8 caracteres del SHA del commit; identifica unívocamente la versión |
| `$CI_JOB_TOKEN` | `<token efímero>` | Permite al bot hacer `git push` sin necesidad de SSH keys manuales |
| `$CI_PROJECT_PATH` | `serenidad/serenidad-platform` | Ruta del proyecto en GitLab; usada para construir la URL de git push |
| `$CI_SERVER_HOST` | `gitlab.com` | Host del servidor GitLab |
| `$CI_PIPELINE_SOURCE` | `push` / `merge_request_event` | Diferencia entre un MR y un push directo |
| `$CI_COMMIT_BRANCH` | `main` | Nombre de la rama del commit actual |

**Variable `CLOUDFLARE_API_TOKEN`:** Esta variable debe tener un token con los siguientes scopes en Cloudflare:
- `Account → Workers Scripts: Edit`
- `Account → Cloudflare Pages: Edit`
- `Zone → Zone: Read` (para verificar el estado del deployment)

## Criterios de Aceptación

| ID | Criterio | Verificación |
|----|----------|--------------|
| CA-09.1.8 | Pipeline de BFF solo se activa con cambios en `apps/bff/` | Push a `apps/web/` no ejecuta `deploy-bff` |
| CA-09.1.9 | `bun run tsc --noEmit` pasa sin errores antes del deploy del BFF | El job no avanza a `wrangler deploy` si hay errores de TypeScript |
| CA-09.1.10 | BFF deployment visible en Cloudflare dashboard | `wrangler deployments list` en `apps/bff/` muestra el deployment activo |
| CA-09.1.11 | `GET https://api.sereni.dad/bff/health` retorna HTTP 200 tras el deploy | Health check en el script del job retorna OK |
| CA-09.1.12 | Pipeline de SPA solo se activa con cambios en `apps/web/` | Push a `apps/bff/` no ejecuta `deploy-web` |
| CA-09.1.13 | `dist/_worker.js` generado por el build de Qwik | El job verifica la existencia del archivo antes del deploy |
| CA-09.1.14 | `https://app.sereni.dad` responde con `Content-Type: text/html` tras el deploy | Health check en el script del job retorna OK |
| CA-09.1.15 | Pushes a `docs/` o a la raíz no ejecutan ningún job de edge | Verificación manual con los commits de prueba |
