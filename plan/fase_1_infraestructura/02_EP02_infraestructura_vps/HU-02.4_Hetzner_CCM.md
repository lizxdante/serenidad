# HU-02.4 — Hetzner Cloud Controller Manager (CCM)

## Descripción General

Por defecto, Kubernetes no conoce el entorno de nube en el que está ejecutándose. El **Cloud Controller Manager (CCM) de Hetzner** actúa como puente entre la API de Kubernetes y la API de Hetzner Cloud, habilitando dos capacidades fundamentales:

1. **Inicialización de nodos:** Elimina el taint `node.cloudprovider.kubernetes.io/uninitialized: NoSchedule` que Talos coloca en el nodo al arrancar, y añade labels de topología con la región y datacenter de Hetzner.

2. **Provisión de LoadBalancers:** Cuando futuras aplicaciones solicitan un Service de tipo `LoadBalancer`, el CCM crea automáticamente un Load Balancer en Hetzner Cloud. (No se usa en Fase 1 — Traefik usa HostPort, pero es necesario para futuras fases.)

---

## Ejecución Detallada

### T-02.4.1 — Crear el namespace y el secret del token de Hetzner

El CCM necesita el token de la API de Hetzner para gestionar recursos en nombre del cluster.

```bash
source .envrc
export KUBECONFIG="$(pwd)/infra/clusters/hetzner-prod/kubeconfig"

# Crear el namespace dedicado para el CCM
kubectl create namespace hcloud-system

# Crear el secret con el token de Hetzner
# La clave "network" se deja vacía porque no se usa Hetzner Private Networks en Fase 1
kubectl create secret generic hcloud \
  --from-literal=token="${HCLOUD_TOKEN}" \
  --from-literal=network="" \
  --namespace=hcloud-system

# Verificar que el secret fue creado con las 2 claves esperadas
kubectl get secret hcloud -n hcloud-system -o json | jq '.data | keys'
# Debe mostrar: ["network", "token"]

kubectl describe secret hcloud -n hcloud-system
# Verificar que "token" tiene datos (Data: N bytes)
```

---

### T-02.4.2 — Desplegar el Cloud Controller Manager

```bash
# Desplegar el CCM usando el manifiesto oficial de Hetzner
# Se usa la variante "ccm.yaml" (sin redes privadas)
kubectl apply -f https://github.com/hetznercloud/hcloud-cloud-controller-manager/releases/latest/download/ccm.yaml

# Esperar a que el Deployment esté disponible
kubectl rollout status deployment/hcloud-cloud-controller-manager \
  -n hcloud-system \
  --timeout=120s

# Verificar que el pod está en estado Running
kubectl get pods -n hcloud-system
# Debe mostrar: hcloud-cloud-controller-manager-xxx   1/1   Running
```

---

### T-02.4.3 — Verificar la integración con Hetzner Cloud

```bash
# 1. Verificar que el taint de inicialización fue eliminado
kubectl describe node serenidad-prod-01 | grep -A3 "Taints:"
# Resultado esperado: "Taints:  <none>"
# Si aún muestra "node.cloudprovider.kubernetes.io/uninitialized", esperar 30s más

# 2. Verificar que el CCM aplicó las labels de topología de Hetzner
kubectl get node serenidad-prod-01 -o json | jq '.metadata.labels | with_entries(select(.key | startswith("topology")))'
# Resultado esperado:
# {
#   "topology.kubernetes.io/region": "eu-central",
#   "topology.kubernetes.io/zone": "eu-central-nbg1-dc3"
# }

# 3. Verificar labels adicionales de la nube
kubectl get node serenidad-prod-01 -o json | jq '.metadata.labels | with_entries(select(.key | startswith("node.kubernetes.io")))'
# Resultado esperado:
# {
#   "node.kubernetes.io/instance-type": "cx32"
# }

# 4. Verificar que los logs del CCM no muestran errores
kubectl logs deployment/hcloud-cloud-controller-manager \
  -n hcloud-system \
  --tail=50 \
  | grep -v "^I"  # Filtrar líneas de INFO, mostrar solo WARN/ERROR
# No debe haber errores de autenticación ni de conectividad

# 5. Verificar que el nodo aparece en el proveedor de nube con su tipo correcto
kubectl get node serenidad-prod-01 -o jsonpath='{.spec.providerID}'
# Resultado esperado: "hcloud://serenidad-prod-01"
```

**Troubleshooting:**

- Si el pod no inicia con `ImagePullBackOff`: verificar conectividad a `ghcr.io` desde el cluster.
- Si el taint persiste: verificar que el secret `hcloud` en el namespace `hcloud-system` contiene el token correcto con `kubectl get secret hcloud -n hcloud-system -o jsonpath='{.data.token}' | base64 -d`.
- Si los logs muestran `401 Unauthorized`: el `HCLOUD_TOKEN` en el secret es incorrecto. Recrear el secret con el token correcto.

## Criterios de Aceptación

| ID | Criterio | Verificación |
|----|----------|--------------|
| CA-02.4.1 | Secret `hcloud` creado en namespace `hcloud-system` con claves `token` y `network` | `kubectl get secret hcloud -n hcloud-system -o json \| jq '.data \| keys'` |
| CA-02.4.2 | Pod del CCM en estado `Running` | `kubectl get pods -n hcloud-system` → `1/1 Running` |
| CA-02.4.3 | Taint `node.cloudprovider.kubernetes.io/uninitialized` eliminado del nodo | `kubectl describe node serenidad-prod-01 \| grep Taints` → `<none>` |

| CA-02.4.5 | `spec.providerID` del nodo apunta al servidor de Hetzner | `kubectl get node serenidad-prod-01 -o jsonpath='{.spec.providerID}'` → `hcloud://serenidad-prod-01` |
| CA-02.4.6 | Logs del CCM sin errores de autenticación o conectividad | `kubectl logs deployment/hcloud-cloud-controller-manager -n hcloud-system` sin líneas de error |

## Definition of Done

- [ ] El CCM de Hetzner está desplegado y en estado `Running`
- [ ] El taint de inicialización ha sido eliminado del nodo `serenidad-prod-01`
- [ ] Las labels de topología (`region`, `zone`, `instance-type`) están presentes en el nodo
- [ ] El campo `providerID` del nodo apunta correctamente al servidor de Hetzner
- [ ] Kubernetes y Hetzner Cloud operan como un sistema unificado con contexto de nube
