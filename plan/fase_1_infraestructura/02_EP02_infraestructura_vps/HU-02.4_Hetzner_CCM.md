# HU-02.4 — Hetzner Cloud Controller Manager (CCM)

## Descripción General
Por defecto Kubernetes "no sabe dónde está". Al instalar el Cloud Controller Manager, un microservicio interno actuará como puente integrador usando nuestra llave API de Hetzner.

### ¿Qué infraestructura tocamos?
- **Etiquetas de Nodos**: El CCM le agregará "labels" al nodo indicando la región (`eu-central`), tipo de máquina y data center donde habita. Removerá el flag de "Node Uninitialized".
- **Hetzner Cloud Network**: En el futuro, cuando Kubernetes pida balanceadores de carga "LoadBalancer", el CCM creará el recurso en la nube Hetzner enviando una instrucción de forma totalmente autónoma.

---

## Ejecución Detallada

### T-02.4.1 — Identidad del Cluster ante la nube
Nos posicionamos dentro del contexto de kubernetes con nuestro `.envrc` activo. 

Crea el espacio y el secreto conteniendo tu token para que el CCM lo asuma e interactúe como si fuese un administrador ante Hetzner:
```bash
kubectl create namespace hcloud-system

# Enlazamos el string del token de HCLOUD que tenemos suelto en la RAM y se lo injectamos adentro a K8s con Base64
kubectl create secret generic hcloud -n hcloud-system \
  --from-literal=token=$HCLOUD_TOKEN \
  --from-literal=network=""
```

### T-02.4.2 — Despliegue del Sistema CCM
Descargamos los manifiestos base oficiales con reglas (Roles, ServiceAccounts) del controlador provisto por Hetzner y lo aplicamos:
```bash
kubectl apply -f https://github.com/hetznercloud/hcloud-cloud-controller-manager/releases/latest/download/ccm-networks.yaml
```

### T-02.4.3 — Validación Operativa

Validamos que el Pod haya levantado limpiamente (Running):
```bash
kubectl get pods -n hcloud-system
```

Verificamos que el agente leyó exitosamente el servidor enviando información geográfica a Kubernetes:
```bash
kubectl get node serenidad-prod-01 -o yaml | grep topology.kubernetes.io
```
Deberías ver una salida conteniendo `topology.kubernetes.io/region: eu-central` y menciones del datacenter (nbg1 ó hel1). 

Asimismo, verificamos que el "taint" (la mancha que bloquea pods diciendo `node.cloudprovider.kubernetes.io/uninitialized: NoSchedule`) se haya difuminado y desaparecido:
```bash
kubectl describe node serenidad-prod-01 | grep Taint
# Respuesta esperada: Taints: <none>
```

Con esto, nuestra nube Hetzner y Kubernetes ahora trabajan como un ente unificado con "contexto híbrido".
