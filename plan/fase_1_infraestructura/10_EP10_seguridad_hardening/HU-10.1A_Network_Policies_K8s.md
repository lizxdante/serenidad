# HU-10.1 (Parte A): Hardening Interno con K8s Network Policies (Zero Trust)

## Descripción General
Actualmente nuestro clúster es un entorno "plano"; cualquier microservicio (un pod comprometido) puede escanear y comunicarse con nuestra base de datos.
Para llegar al grado de certificación médica y blindar los datos, implementaremos el principio **Deny-All (Zero Trust)**. Se denegará radicalmente cualquier tráfico interno en los *namespaces* de producción (`serenidad-core` y `serenidad-data`), permitiendo exclusivamente el paso a través de túneles lógicos definidos explícitamente (Whitelisting). 

> [!WARNING]
> La aplicación de directivas Zero-Trust de forma asíncrona puede cortar el flujo actual. Generaremos todos los manifiestos de denegación y permisibilidad en una sola operación de compilación antes de empujarlos al clúster para no causar *downtime*.

---

## Ejecución Detallada

### T-10.1.1 a T-10.1.6 — Definir Mapeo de Red Declarativo
Escribiremos todas las vías por un único archivo por practicidad de lectura en esta fase. Construimos las tuberías que habilitarán el tráfico estricto:

```bash
mkdir -p infra/infrastructure/network-policies

cat <<EOF > infra/infrastructure/network-policies/policies.yaml
# ---------------------------------------------------------
# BLOQUE 1: ESTRATEGIA DENY-ALL POR DEFECTO
# ---------------------------------------------------------
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: serenidad-core
spec:
  podSelector: {} # Selecciona todos los pods del namespace
  policyTypes:
    - Ingress
    - Egress
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: serenidad-data
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
---
# ---------------------------------------------------------
# BLOQUE 2: EXCEPCIÓN DNS INTERNO (Ambos namespaces)
# Sin esto, los servicios no podrian convertir URLs a IPs.
# ---------------------------------------------------------
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: serenidad-core
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: serenidad-data
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - protocol: UDP
          port: 53
---
# ---------------------------------------------------------
# BLOQUE 3: COMUNICACIÓN CRÍTICA INTRA Y EXTRA SERVICIOS
# ---------------------------------------------------------
# 1. Traefik -> IAM Service
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-traefik-to-iam
  namespace: serenidad-core
spec:
  podSelector:
    matchLabels:
      app: iam-service
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: traefik
      ports:
        - protocol: TCP
          port: 8080
---
# 2. IAM Service y Kratos -> PostgreSQL (Core -> Data)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-core-to-postgres
  namespace: serenidad-data
spec:
  podSelector:
    matchLabels:
      "cnpg.io/cluster": serenidad-pg
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: serenidad-core
      ports:
        - protocol: TCP
          port: 5432
---
# 3. Flujo interno: IAM -> Kratos Admin API
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-iam-to-kratos
  namespace: serenidad-core
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: kratos
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: iam-service
      ports:
        - protocol: TCP
          port: 4434
---
# 4. Flujo externo: PostgreSQL a Backblaze B2 (Egress Público para BD)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-cnpg-to-s3
  namespace: serenidad-data
spec:
  podSelector:
    matchLabels:
      "cnpg.io/cluster": serenidad-pg
  policyTypes:
    - Egress
  egress:
    - ports:
        - protocol: TCP
          port: 443
EOF
```
*(Nota de ingeniería: Los Egress Externos de Cert-Manager y Traefik no son impactados puesto que Cert-Manager y Traefik habitan en espacios de nombres distintos que no estamos endureciendo en esta fase con Deny-All).*

### T-10.1.7 — Sellar el Escudo vía GitOps
Añadimos este grupo de reglas a Kustomize para someterlas atomicamente. Como el cluster procesará las denegaciones y los permisos en paralelo, Kubernetes computará efectivamente el tráfico sin tirar los pods.

```bash
cat <<EOF > infra/infrastructure/network-policies/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - policies.yaml
EOF

git add infra/infrastructure/network-policies/
git commit -m "feat(security): implement layer 4 zero trust network policies ensuring isolation of production namespaces"
git push origin main
flux reconcile kustomization flux-system --with-source
```

### T-10.1.9 — Auditoría Anti-Escalado e Invasión
Revisaremos la impenetrabilidad lanzando un intento de intrusión desde un Pod ajeno (`namespace: default`).

```bash
# Lanza un container limpio temporal en 'default' que no está en la Whitelist e intenta hacer ping 
# a la base de datos PostgreSQL alojada en 'serenidad-data'.
kubectl run temp-hacker --rm -i --tty --image=alpine --namespace=default -- sh
# (Dentro del nuevo pod alpino ejecutar):
nc -zv serenidad-pg-rw.serenidad-data.svc.cluster.local 5432
# DEBERÍA GENERAR TIMEOUT/FALLO. Ctrl+C para abortar. Sal (exit) para borrar el pod temporal.

# Ahora verifiquemos si la comunicación válida no se rompió chequeando si la salud del IAM se mantiene:
kubectl exec -it deployment/iam-service -n serenidad-core -- wget -qO- http://localhost:8080/ready
# DEBERÍA RETORNAR {"status":"ok","db":"connected","kratos":"reachable"} indicando que sus 
# tuberias a Kratos y su tubería cruzando al namespace Data fueron respetadas positivamente de los Policies.
```
