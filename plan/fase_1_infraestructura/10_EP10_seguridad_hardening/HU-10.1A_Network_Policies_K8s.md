# HU-10.1 (Parte A) — Hardening Interno: Network Policies Zero Trust en Kubernetes

## Descripción General

Sin Network Policies, Kubernetes opera en un modelo de red "plano": cualquier Pod en cualquier namespace puede establecer conexiones TCP con cualquier otro Pod del cluster. Un Pod comprometido (por inyección de dependencias, vulnerabilidad en imagen, o escape de contenedor) podría escanear y atacar la base de datos directamente.

Las **Kubernetes Network Policies** implementan segmentación de red en Capa 4 (TCP/UDP), aplicada por el CNI (Flannel/Cilium/Calico). En Talos Linux con Flannel, las NetworkPolicies se aplican mediante el componente integrado de kube-proxy.

### Modelo Zero Trust aplicado

La estrategia es **deny-all primero, allowlist después**:

1. Policies `deny-all` en `serenidad-core` y `serenidad-data` bloquean todo Ingress y Egress por defecto
2. Policies de excepción abren únicamente los flujos estrictamente necesarios
3. El DNS interno (port 53/UDP hacia `kube-system`) se habilita en ambos namespaces — sin esto, la resolución de service discovery falla

### Mapa de flujos permitidos

```
Internet → Traefik (traefik ns) → IAM Service (serenidad-core) → Kratos admin (serenidad-core)
                                                               ↘ PostgreSQL (serenidad-data)
Kratos public (serenidad-core) → PostgreSQL (serenidad-data)

PostgreSQL (serenidad-data) → Backblaze B2 (Internet, TCP 443) [WAL archiving]

Todos los pods en serenidad-core y serenidad-data → kube-system:53 [DNS]
```

> **ADVERTENCIA:** Las Network Policies deben aplicarse atómicamente (todas las policies de deny y allow en un solo commit/apply). Aplicar `deny-all` sin las excepciones correspondientes en el mismo `kubectl apply` causará downtime inmediato. El método GitOps garantiza que Kubernetes procesa el conjunto completo como una transacción.

### T-10.1.2 — Definir todas las Network Policies en un manifiesto

```bash
cat > infra/infrastructure/network-policies/policies.yaml << 'EOF'
# =============================================================================
# Network Policies — Modelo Zero Trust para serenidad-platform
# Aplicar SIEMPRE de forma atómica (todas las policies juntas).
# =============================================================================

# ── BLOQUE 1: DENY-ALL POR DEFECTO ───────────────────────────────────────────
# Bloquea TODO el tráfico Ingress y Egress en serenidad-core.
# Solo las policies de excepción posteriores abren flujos específicos.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-default
  namespace: serenidad-core
spec:
  podSelector: {}   # Selecciona TODOS los pods del namespace
  policyTypes:
    - Ingress
    - Egress
---
# Bloquea TODO el tráfico en serenidad-data (namespace de base de datos).
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-default
  namespace: serenidad-data
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
---

# ── BLOQUE 2: EXCEPCIÓN DNS INTERNO ──────────────────────────────────────────
# Sin esta excepción, los pods no pueden resolver nombres de servicio K8s.
# CoreDNS vive en kube-system y escucha en UDP+TCP 53.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: serenidad-core
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: serenidad-data
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
---

# ── BLOQUE 3: FLUJOS DE INGRESS AUTORIZADOS ───────────────────────────────────

# 3.1 Traefik → IAM Service
# Traefik (namespace: traefik) actúa como proxy inverso para el IAM Service.
# Permite conexiones entrantes desde cualquier pod del namespace traefik.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-traefik-to-iam
  namespace: serenidad-core
spec:
  podSelector:
    matchLabels:
      app: iam-service
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: traefik
      ports:
        - protocol: TCP
          port: 8080
---
# 3.2 Traefik → Kratos (endpoint público)
# El endpoint público de Kratos en :4433 recibe tráfico de Traefik.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-traefik-to-kratos-public
  namespace: serenidad-core
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: kratos
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: traefik
      ports:
        - protocol: TCP
          port: 4433
---
# 3.3 IAM Service → Kratos Admin API
# El IAM Service llama a la Admin API de Kratos (:4434) para:
#   - Verificar sesiones (ForwardAuth)
#   - Obtener identidades tras el token exchange
# Esta policy permite el flujo intra-namespace serenidad-core.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-iam-to-kratos-admin
  namespace: serenidad-core
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: kratos
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: iam-service
      ports:
        - protocol: TCP
          port: 4434
---

# ── BLOQUE 4: ACCESO A POSTGRESQL (serenidad-data) ────────────────────────────

# 4.1 serenidad-core → PostgreSQL
# IAM Service y Kratos (ambos en serenidad-core) necesitan acceso a PostgreSQL.
# La policy está en serenidad-data y permite ingress desde el namespace entero
# de serenidad-core (cualquier pod con las labels correctas en ese namespace).
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-core-to-postgres
  namespace: serenidad-data
spec:
  podSelector:
    matchLabels:
      cnpg.io/cluster: serenidad-pg
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: serenidad-core
      ports:
        - protocol: TCP
          port: 5432
---

# ── BLOQUE 5: EGRESS AUTORIZADO ───────────────────────────────────────────────

# 5.1 IAM Service → Egress hacia Kratos admin (intra-namespace)
# El IAM Service debe poder iniciar conexiones hacia Kratos :4434.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-iam-egress-to-kratos
  namespace: serenidad-core
spec:
  podSelector:
    matchLabels:
      app: iam-service
  policyTypes:
    - Egress
  egress:
    - to:
        - podSelector:
            matchLabels:
              app.kubernetes.io/name: kratos
      ports:
        - protocol: TCP
          port: 4434
    # Egress hacia serenidad-data (PostgreSQL)
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: serenidad-data
      ports:
        - protocol: TCP
          port: 5432
---
# 5.2 Kratos → Egress hacia PostgreSQL y hacia Internet (courier SMTP via Resend)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-kratos-egress
  namespace: serenidad-core
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: kratos
  policyTypes:
    - Egress
  egress:
    # PostgreSQL
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: serenidad-data
      ports:
        - protocol: TCP
          port: 5432
    # Resend SMTP API (TLS 465 y HTTPS 443) para envío de emails
    - ports:
        - protocol: TCP
          port: 443
        - protocol: TCP
          port: 465
---
# 5.3 CloudNativePG → Backblaze B2 para WAL archiving
# Los pods de PostgreSQL hacen egress a Internet (B2 S3-compatible, TCP 443).
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-cnpg-egress-to-b2
  namespace: serenidad-data
spec:
  podSelector:
    matchLabels:
      cnpg.io/cluster: serenidad-pg
  policyTypes:
    - Egress
  egress:
    - ports:
        - protocol: TCP
          port: 443
EOF
```

### T-10.1.3 — Crear el Kustomization para FluxCD

```bash
cat > infra/infrastructure/network-policies/kustomization.yaml << 'EOF'
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - policies.yaml
EOF
```

Verificar que la kustomization raíz de infraestructura incluya este directorio:

```bash
# infra/infrastructure/kustomization.yaml debe incluir:
# - network-policies/
grep "network-policies" infra/infrastructure/kustomization.yaml || \
  echo "  - network-policies/" >> infra/infrastructure/kustomization.yaml
```

### T-10.1.4 — Commit y despliegue GitOps

```bash
git add infra/infrastructure/network-policies/

git commit -m "feat(security): implement Zero Trust Layer-4 NetworkPolicies for serenidad-core and serenidad-data

- deny-all-default in both production namespaces
- allowlist: Traefik → IAM, Traefik → Kratos public
- allowlist: IAM → Kratos admin API (:4434)
- allowlist: IAM + Kratos → PostgreSQL (:5432)
- allowlist: CloudNativePG → Backblaze B2 (:443) for WAL archiving
- DNS egress (UDP/TCP :53 → kube-system) in both namespaces"

git push origin main

# Forzar reconciliación inmediata de FluxCD
flux reconcile kustomization flux-system --with-source

# Esperar a que las Network Policies se apliquen
kubectl get networkpolicies -n serenidad-core
kubectl get networkpolicies -n serenidad-data
```

### T-10.1.6 — Auditoría de penetración interna

```bash
# ── Test 1: Acceso no autorizado desde 'default' namespace ───────────────────
# Un atacante que controle un Pod en 'default' no debe poder conectarse a PostgreSQL.
kubectl run penetration-test \
  --rm -i --tty \
  --image=alpine \
  --namespace=default \
  --restart=Never \
  -- sh -c "nc -zv -w5 serenidad-pg-rw.serenidad-data.svc.cluster.local 5432; echo 'Exit: '$?"
# Resultado esperado: timeout después de 5 segundos + "Exit: 1" (connection refused/timeout)
# Si se conecta exitosamente, la policy deny-all NO está funcionando.

# ── Test 2: Servicios legítimos siguen funcionando ─────────────────────────────
# El IAM Service debe seguir respondiendo al health check (sus conexiones a DB y Kratos están permitidas)
kubectl exec -n serenidad-core deployment/iam-service -- \
  wget -qO- http://localhost:8080/ready
# Resultado esperado: {"status":"ok","db":"connected","kratos":"reachable"}

# ── Test 3: DNS interno funcionando en ambos namespaces ──────────────────────
kubectl run dns-test \
  --rm -i \
  --image=alpine \
  --namespace=serenidad-core \
  --restart=Never \
  -- sh -c "nslookup kubernetes.default.svc.cluster.local && echo 'DNS OK'"
# Resultado esperado: resolución exitosa del nombre interno

# ── Test 4: Verificar el tráfico a PostgreSQL desde serenidad-core ────────────
kubectl exec -n serenidad-core deployment/iam-service -- \
  sh -c "nc -zv -w3 serenidad-pg-rw.serenidad-data.svc.cluster.local 5432 && echo 'PG reachable'"
# Resultado esperado: "PG reachable" (el flujo serenidad-core → serenidad-data está permitido)
```
