# HU-11.1 — Observabilidad Inicial y Monitorización

## Descripción General

La observabilidad es la capacidad de inferir el estado interno del sistema a partir de sus outputs externos. Antes de declarar el sistema en producción, se requiere:

1. **Health checks en microservicios:** Kubernetes necesita señales para decidir si reiniciar o excluir del balanceo un Pod que dejó de funcionar.
2. **Alertas de infraestructura:** Notificaciones automáticas ante anomalías del VPS (CPU, disco, red) antes de que el usuario experimente degradación.
3. **Comandos de diagnóstico operacional:** Glosario de comandos verificados para responder a incidentes en menos de 2 minutos.

### Estándar de health endpoints

Todos los microservicios del backend (Go) deben implementar 3 endpoints HTTP:

| Endpoint | Tipo | Propósito K8s | Comportamiento esperado |
|---|---|---|---|
| `GET /health` | Liveness | Si el proceso sigue vivo. Fallo → K8s reinicia el Pod | HTTP 200 siempre que el proceso responda; HTTP 5xx en pánico/deadlock |
| `GET /ready` | Readiness | Si el Pod puede recibir tráfico. Fallo → K8s lo excluye del Service | HTTP 200 cuando DB y dependencias están alcanzables; HTTP 503 en reconexión |
| `GET /metrics` | Metrics | Telemetría en formato OpenMetrics (Prometheus) | Expuesto solo internamente; no debe ser accesible desde Traefik sin autenticación |

### T-11.1.1 — Implementar el estándar de health en el IAM Service

El IAM Service (HU-07.2) ya tiene la estructura; verificar que los handlers están implementados correctamente:

```go
// services/iam/internal/delivery/http/health.go
package http

import (
  "encoding/json"
  "net/http"
  "time"

  "gitlab.com/serenidad/serenidad-platform/services/iam/internal/infrastructure/db"
  "gitlab.com/serenidad/serenidad-platform/services/iam/internal/infrastructure/kratos"
)

type HealthHandler struct {
  db     *db.Pool
  kratos *kratos.Client
  version string
}

type healthResponse struct {
  Status  string `json:"status"`
  Service string `json:"service"`
  Version string `json:"version,omitempty"`
}

type readyResponse struct {
  Status string `json:"status"`
  DB     string `json:"db"`
  Kratos string `json:"kratos"`
}

// LivenessHandler: el proceso está vivo si puede responder.
// K8s llama a este endpoint periódicamente; si falla 3 veces seguidas, reinicia el Pod.
func (h *HealthHandler) LivenessHandler(w http.ResponseWriter, r *http.Request) {
  w.Header().Set("Content-Type", "application/json")
  json.NewEncoder(w).Encode(healthResponse{
    Status:  "ok",
    Service: "iam-service",
    Version: h.version,
  })
}

// ReadinessHandler: el Pod está listo cuando puede conectarse a sus dependencias.
// Traefik excluye el Pod del balanceo si este endpoint retorna no-200.
func (h *HealthHandler) ReadinessHandler(w http.ResponseWriter, r *http.Request) {
  w.Header().Set("Content-Type", "application/json")

  dbStatus := "connected"
  kratosStatus := "reachable"
  allOk := true

  // Verificar conectividad a PostgreSQL (ping con timeout corto)
  ctx := r.Context()
  if err := h.db.PingContext(ctx); err != nil {
    dbStatus = "unreachable"
    allOk = false
  }

  // Verificar conectividad a Kratos Admin API (HEAD request)
  kratosCtx, cancel := context.WithTimeout(ctx, 2*time.Second)
  defer cancel()
  if err := h.kratos.HealthCheck(kratosCtx); err != nil {
    kratosStatus = "unreachable"
    allOk = false
  }

  resp := readyResponse{
    Status: "ok",
    DB:     dbStatus,
    Kratos: kratosStatus,
  }

  if !allOk {
    resp.Status = "degraded"
    w.WriteHeader(http.StatusServiceUnavailable)
  }

  json.NewEncoder(w).Encode(resp)
}
```

### T-11.1.2 — Configurar probes en el Deployment de K8s

Los probes se definen en `infra/apps/iam-service/deployment.yaml`:

```yaml
# infra/apps/iam-service/deployment.yaml (fragmento de probes)
spec:
  template:
    spec:
      containers:
        - name: iam-service
          image: registry.gitlab.com/serenidad/serenidad-platform/iam-service:INITIAL_SHA
          ports:
            - containerPort: 8080
              name: http
          # startupProbe: da tiempo al servicio para inicializar (migraciones, conexiones)
          # Hasta 60 segundos antes de que liveness tome el control
          startupProbe:
            httpGet:
              path: /health
              port: http
            failureThreshold: 12
            periodSeconds: 5
          # livenessProbe: si falla 3 veces → K8s reinicia el contenedor
          livenessProbe:
            httpGet:
              path: /health
              port: http
            initialDelaySeconds: 0   # startupProbe ya garantizó el arranque
            periodSeconds: 30
            failureThreshold: 3
            timeoutSeconds: 5
          # readinessProbe: si falla → K8s no envía tráfico a este Pod
          readinessProbe:
            httpGet:
              path: /ready
              port: http
            initialDelaySeconds: 0
            periodSeconds: 10
            failureThreshold: 3
            successThreshold: 1
            timeoutSeconds: 5
```

### T-11.1.3 — Verificar los health endpoints en producción

```bash
# 1. Verificar liveness directamente en el Pod (sin pasar por Traefik)
kubectl exec -n serenidad-core deployment/iam-service -- \
  wget -qO- http://localhost:8080/health
# {"status":"ok","service":"iam-service","version":"a1b2c3d4"}

# 2. Verificar readiness (valida DB + Kratos)
kubectl exec -n serenidad-core deployment/iam-service -- \
  wget -qO- http://localhost:8080/ready
# {"status":"ok","db":"connected","kratos":"reachable"}

# 3. Verificar a través de Traefik (endpoint protegido por JWT)
curl -s https://api.sereni.dad/api/iam/health
# {"status":"ok","service":"iam-service","version":"a1b2c3d4"}

# 4. Verificar que K8s reporta los probes como exitosos
kubectl describe pod -n serenidad-core -l app=iam-service \
  | grep -A5 "Liveness\|Readiness\|Startup"
# Liveness:   http-get http://:http/health ...
# Readiness:  http-get http://:http/ready ...
```

### T-11.1.4 — Configurar alertas de infraestructura en Hetzner Cloud

Las alertas de Hetzner se configuran en el panel web (no hay API para este propósito en la versión gratuita):

1. Acceder a [console.hetzner.cloud](https://console.hetzner.cloud/)
2. Seleccionar `serenidad-prod-01`
3. Ir a la pestaña `Graphs` (Monitoring)
4. Configurar las siguientes alertas enviando notificaciones al email del equipo de DevOps:

| Métrica | Umbral | Duración | Acción |
|---|---|---|---|
| **CPU Usage** | `> 85%` | Sostenido 5 minutos | Email al equipo; revisar `kubectl top pods -A` |
| **Disk I/O** | `> 200 MB/s` | Sostenido 2 minutos | Posible carga de WAL o backup; revisar CloudNativePG |
| **Network In** | `> 500 Mbps` | Sostenido 3 minutos | Posible ataque DDoS; Cloudflare debería filtrar antes |
| **Availability** | Ping falla | `> 30 segundos` | VPS caído; iniciar DR playbook (HU-11.3) |

**Nota:** Para monitorización más avanzada (métricas a nivel de Pod, alertas basadas en `/metrics`), considerar Prometheus + Grafana + Alertmanager en la Fase 2.

### T-11.1.5 — Instalar glosario de aliases operacionales

```bash
# Agregar al ~/.zshrc o ~/.bashrc del operador del cluster
cat >> ~/.zshrc << 'EOF'

# ── serenidad cluster operations ─────────────────────────────────────────────

# Pods no saludables en todos los namespaces
alias kp-broken="kubectl get pods -A | grep -vE 'Running|Completed|Succeeded'"

# Estado de todos los HelmReleases y Kustomizations de FluxCD
alias flux-status="flux get all -A"

# Solo los recursos de FluxCD con problemas
alias flux-broken="flux get all -A --status-selector ready=false"

# Pods ordenados por consumo de RAM (requiere metrics-server)
alias ktop="kubectl top pods -A --sort-by=memory"

# Últimos 20 eventos del cluster ordenados por timestamp
alias kevents="kubectl get events -A --sort-by='.lastTimestamp' | tail -20"

# Estado del cluster de PostgreSQL (CloudNativePG)
alias pg-status="kubectl get cluster,backup,scheduledbackup -n serenidad-data"

# Logs del IAM Service en tiempo real
alias iam-logs="kubectl logs -f deployment/iam-service -n serenidad-core"

# Logs de Kratos en tiempo real
alias kratos-logs="kubectl logs -f deployment/kratos -n serenidad-core"

# Resumen rápido del estado general
alias cluster-health="echo '=== NODES ===' && kubectl get nodes && \
  echo '=== BROKEN PODS ===' && kubectl get pods -A | grep -vE 'Running|Completed|Succeeded' && \
  echo '=== FLUX ===' && flux get all -A --status-selector ready=false 2>/dev/null || true"
EOF

source ~/.zshrc
```

### T-11.1.6 — Comandos de diagnóstico esenciales

```bash
# ── Diagnóstico general del cluster ──────────────────────────────────────────

# ¿Qué está roto?
kubectl get pods -A | grep -vE "Running|Completed|Succeeded"

# ¿Qué eventos recientes hubo?
kubectl get events -A --sort-by='.lastTimestamp' | tail -30

# ¿Qué consume más recursos?
kubectl top pods -A --sort-by=memory | head -20
kubectl top nodes

# ── FluxCD ────────────────────────────────────────────────────────────────────

# Estado de todos los objetos de FluxCD
flux get all -A

# Forzar reconciliación inmediata
flux reconcile source git flux-system
flux reconcile kustomization flux-system --with-source

# Ver logs del controlador de FluxCD
kubectl logs -n flux-system deployment/source-controller | tail -50
kubectl logs -n flux-system deployment/helm-controller | tail -50

# ── CloudNativePG ─────────────────────────────────────────────────────────────

# Estado del cluster de PostgreSQL
kubectl get cluster -n serenidad-data serenidad-pg -o wide

# Últimos backups y su estado
kubectl get backup -n serenidad-data --sort-by='.metadata.creationTimestamp'

# Verificar WAL archiving (debe mostrar archivos recientes en B2)
kubectl exec -n serenidad-data serenidad-pg-1 -- \
  psql -U postgres -c "SELECT pg_current_wal_lsn(), pg_walfile_name(pg_current_wal_lsn());"

# ── IAM Service ───────────────────────────────────────────────────────────────

# Logs de los últimos 15 minutos
kubectl logs deployment/iam-service -n serenidad-core --since=15m

# Logs de todos los pods del deployment (útil tras un rollout)
kubectl logs deployment/iam-service -n serenidad-core --all-containers=true

# Ejecutar un comando dentro del pod (imagen Distroless — shell limitado)
# Nota: la imagen Distroless no tiene bash; usar kubectl debug para debugging
kubectl debug -it deployment/iam-service -n serenidad-core \
  --image=alpine --target=iam-service -- sh

# ── Traefik ───────────────────────────────────────────────────────────────────

# Abrir el dashboard de Traefik localmente (sin exponer a Internet)
kubectl port-forward -n traefik daemonset/traefik 9000:9000
# Luego abrir http://localhost:9000 en el navegador

# Verificar IngressRoutes activas
kubectl get ingressroute -A
```

| ID | Criterio | Verificación |
