# HU-11.2 — Operaciones de Día 2

## Descripción General

Las operaciones de "Día 2" son las actividades del ciclo de vida posterior al aprovisionamiento inicial: despliegues de nuevas versiones, gestión de secretos, rotación de claves criptográficas y actualizaciones del sistema operativo. Con FluxCD gestionando el estado declarativo del cluster, las reglas del juego cambian respecto a un despliegue imperativo tradicional.

### Principios operacionales

| Principio | Implicación |
|---|---|
| **Git es la fuente de verdad** | Toda modificación del cluster debe pasar por un commit a `main` |
| **FluxCD reconcilia, no el operador** | Nunca aplicar `kubectl apply` directamente en producción salvo emergencia |
| **SOPS protege todos los secretos** | Nunca commitear valores en texto plano; siempre cifrar con `encrypt-secret.sh` |
| **Talos es inmutable** | No se instalan paquetes, no se modifica el OS; solo upgrades atómicos de imagen |

## Ejecución Detallada

### T-11.2.1 — Ciclo normal de despliegue de software

El flujo estándar para publicar una nueva versión del IAM Service u otro microservicio Go:

```bash
# ── En el entorno de desarrollo local ─────────────────────────────────────────

# 1. Ejecutar los tests localmente antes del push
cd services/iam
go test -v -race ./...
# Todos los tests deben pasar

# 2. Verificar que no hay errores de tipos
go vet ./...

# 3. Hacer commit y push a main
git add services/iam/
git commit -m "feat(iam): add token revocation endpoint"
git push origin main

# ── GitLab CI/CD (automático, ~5 min) ────────────────────────────────────────
# El pipeline iam-service.yml se activa porque services/iam/ cambió:
# 1. test-iam: go test -race → reporta cobertura
# 2. build-push-iam: docker build → push a registry → actualiza deployment.yaml con nuevo SHA

# ── FluxCD (automático, ~1-3 min después del pipeline) ───────────────────────
# FluxCD detecta el nuevo commit en infra/apps/iam-service/deployment.yaml
# y ejecuta un rolling update del Deployment en Kubernetes

# ── Verificar el despliegue ───────────────────────────────────────────────────
# Observar el rollout en tiempo real
kubectl rollout status deployment/iam-service -n serenidad-core --timeout=120s

# Verificar que el Pod tiene la nueva imagen (debe mostrar el nuevo SHA)
kubectl get deployment iam-service -n serenidad-core \
  -o jsonpath='{.spec.template.spec.containers[0].image}'

# Health check para confirmar que el nuevo Pod está saludable
curl -s https://api.sereni.dad/api/iam/health | jq '.version'
# Debe mostrar el nuevo CI_COMMIT_SHORT_SHA
```

### T-11.2.2 — Ciclo de hotfix de emergencia

> **ADVERTENCIA:** Este procedimiento es exclusivo para situaciones donde producción está caída y el pipeline normal (≥ 5 min) no es admisible. FluxCD revertirá el hotfix en el siguiente ciclo de reconciliación (≤ 10 min) si no se hace un push correcto a `main` inmediatamente después.

```bash
# ── PASO 1: Construir y subir la imagen de hotfix localmente ──────────────────
# (Requiere Docker instalado y autenticación al GitLab Registry)

export REGISTRY="registry.gitlab.com/serenidad/serenidad-platform"
export HOTFIX_TAG="hotfix-$(date -u +%Y%m%dT%H%M%S)"

docker build \
  -t "${REGISTRY}/iam-service:${HOTFIX_TAG}" \
  -f services/iam/Dockerfile \
  services/iam/

docker push "${REGISTRY}/iam-service:${HOTFIX_TAG}"

# ── PASO 2: Aplicar la imagen hotfix directamente en K8s ─────────────────────
# Esto produce un estado divergente respecto a Git — es temporal
kubectl set image deployment/iam-service \
  iam-service="${REGISTRY}/iam-service:${HOTFIX_TAG}" \
  -n serenidad-core

# Verificar que el rollout completó
kubectl rollout status deployment/iam-service -n serenidad-core --timeout=90s

# ── PASO 3: Resolver correctamente el problema en el código ───────────────────
# Hacer el fix real en el código fuente y hacer push a main
# El pipeline de CI/CD creará la imagen correcta y actualizará el manifiesto
# FluxCD reconciliará y reemplazará el hotfix con la versión correcta

# ── PASO 4: Verificar que FluxCD no revirtió a la versión rota ───────────────
# Esperar a que el pipeline de CI/CD complete y FluxCD reconcilie
flux get kustomization serenidad-apps -n flux-system --watch
# Cuando esté Ready: True con el SHA del fix, el ciclo de emergencia terminó
```

### T-11.2.3 — Agregar nuevos secretos al cluster

Nunca se almacenan valores sensibles en texto plano en Git. El flujo estándar usa `encrypt-secret.sh` (EP-03):

```bash
# ── Ejemplo: agregar una nueva clave de API de un servicio externo ────────────

# 1. Cifrar el secreto con SOPS/age y guardarlo en infra/secrets/
./scripts/encrypt-secret.sh serenidad-core nueva-api-key \
  EXTERNAL_SERVICE_TOKEN="sk-prod-xxxxxxxxxxxxx"
# Genera: infra/secrets/serenidad-core/nueva-api-key.yaml (cifrado con age)

# 2. Referenciar el secreto en el Deployment que lo necesita
# En infra/apps/iam-service/deployment.yaml, agregar bajo envFrom o env:
#   envFrom:
#     - secretRef:
#         name: nueva-api-key

# 3. Commitear y dejar que FluxCD lo aplique
git add infra/secrets/serenidad-core/nueva-api-key.yaml
git add infra/apps/iam-service/deployment.yaml
git commit -m "feat(iam): add external API key secret reference"
git push origin main

# 4. Verificar que SOPS Controller descifró e inyectó el secret
kubectl get secret nueva-api-key -n serenidad-core
# NAME            TYPE     DATA   AGE
# nueva-api-key   Opaque   1      Xs

# 5. Verificar que el valor es correcto (base64 decode)
kubectl get secret nueva-api-key -n serenidad-core \
  -o jsonpath='{.data.EXTERNAL_SERVICE_TOKEN}' | base64 -d
# sk-prod-xxxxxxxxxxxxx
```

### T-11.2.4 — Rotación de la clave maestra de SOPS (age)

La clave `age` en `~/.config/sops/age/keys.txt` es la clave maestra que descifra todos los secretos del repositorio. Su compromiso requiere rotación completa inmediata.

**Indicadores de que se necesita rotación:**
- Un miembro del equipo con acceso a la clave abandona el proyecto
- Se sospecha acceso no autorizado al archivo de claves
- Política de seguridad de rotación periódica (recomendado: cada 12 meses)

```bash
# ── PASO 1: Generar nueva clave age ───────────────────────────────────────────
age-keygen -o ~/.config/sops/age/keys-new.txt
# Clave pública (public key): age1xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

# Mostrar la clave pública para copiarla
grep "public key" ~/.config/sops/age/keys-new.txt
# Guardar en el password manager ANTES de continuar

# ── PASO 2: Actualizar .sops.yaml con la nueva clave pública ─────────────────
# Editar infra/secrets/.sops.yaml — reemplazar la clave age antigua por la nueva
cat infra/secrets/.sops.yaml
# Debe tener:
#   creation_rules:
#     - age: >-
#         age1NUEVA_CLAVE_PUBLICA_AQUI

# ── PASO 3: Re-cifrar todos los secretos existentes ───────────────────────────
# Usar ambas claves (antigua + nueva) durante la transición
export SOPS_AGE_KEY_FILE=~/.config/sops/age/keys.txt  # clave vieja para descifrar

# Re-cifrar con la nueva clave (usando la configuración actualizada de .sops.yaml)
for SECRET_FILE in $(find infra/secrets -name "*.yaml" -not -name ".sops.yaml"); do
  echo "Re-cifrando: ${SECRET_FILE}"
  sops --rotate --in-place "${SECRET_FILE}"
done

# ── PASO 4: Actualizar el secret de SOPS en Kubernetes ───────────────────────
# El SOPS Controller en K8s necesita la nueva clave privada para descifrar
kubectl create secret generic sops-age \
  --from-file=age.agekey=~/.config/sops/age/keys-new.txt \
  --namespace flux-system \
  --dry-run=client -o yaml | kubectl apply -f -

# Verificar que el SOPS Controller recarga la nueva clave
kubectl rollout restart deployment/kustomize-controller -n flux-system
kubectl rollout status deployment/kustomize-controller -n flux-system --timeout=60s

# ── PASO 5: Verificar que FluxCD puede descifrar con la nueva clave ───────────
flux reconcile kustomization flux-system --with-source
flux get kustomization -A
# Todos deben estar en Ready: True

# ── PASO 6: Commit y limpieza ─────────────────────────────────────────────────
git add infra/secrets/
git commit -m "security: rotate SOPS age master key — all secrets re-encrypted"
git push origin main

# Reemplazar la clave vieja por la nueva en el sistema local
mv ~/.config/sops/age/keys-new.txt ~/.config/sops/age/keys.txt
# DESTRUIR la clave vieja de forma segura (no simplemente borrar el archivo)
# En macOS: srm -z ~/.config/sops/age/keys-old.txt (si la guardaste con otro nombre)
# En Linux: shred -u -z <archivo>
```

### T-11.2.5 — Actualización del OS de Talos Linux

Talos es un sistema operativo inmutable. Las actualizaciones reemplazan la imagen del OS completa atómicamente. El nodo se reinicia, Kubernetes vuelve a funcionar, y el proceso dura menos de 2 minutos de interrupción.

```bash
# ── PASO 1: Verificar la versión actual ───────────────────────────────────────
talosctl version --nodes ${FLOATING_IP}
# Muestra: Client: v1.10.x / Server: v1.10.x

# ── PASO 2: Consultar las notas de release de la nueva versión ────────────────
# Revisar: https://github.com/siderolabs/talos/releases
# Verificar si la nueva versión requiere actualizar el machineconfig

# ── PASO 3: Obtener la nueva imagen con las mismas extensiones ────────────────
# Usar Talos Image Factory (HU-02.2) para generar la URL de la imagen con qemu-guest-agent
# https://factory.talos.dev/
# Seleccionar la nueva versión y las mismas extensiones (qemu-guest-agent)
# Copiar el installerURL (formato: factory.talos.dev/installer/SCHEMATIC:VERSION)

NEW_VERSION="v1.10.1"  # Ejemplo — ajustar a la versión objetivo
SCHEMATIC_ID="<ID del schematic con qemu-guest-agent>"  # Del Image Factory

INSTALLER_URL="factory.talos.dev/installer/${SCHEMATIC_ID}:${NEW_VERSION}"

# ── PASO 4: Ejecutar el upgrade ───────────────────────────────────────────────
talosctl upgrade \
  --nodes ${FLOATING_IP} \
  --image "${INSTALLER_URL}"

# La conexión se perderá durante ~60-90 segundos mientras el nodo se reinicia
# Esperar a que talosctl vuelva a responder

# ── PASO 5: Verificar el upgrade ─────────────────────────────────────────────
# Puede tardar 2-3 minutos para que el nodo vuelva a estar completamente listo

# Verificar la nueva versión del OS
talosctl version --nodes ${FLOATING_IP}
# Debe mostrar la nueva versión en Server

# Verificar que K8s volvió a funcionar
kubectl get nodes
# serenidad-prod-01   Ready   control-plane   Xd   vX.XX.X

# Verificar que todos los Pods se recuperaron
kubectl get pods -A | grep -vE "Running|Completed|Succeeded"
# No debe haber Pods en estados problemáticos

# Verificar FluxCD
flux get all -A
# Todos los recursos deben estar en Ready: True
```
