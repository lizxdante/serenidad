# HU-11.3 — Troubleshooting y Disaster Recovery

## Descripción General

Este documento es el **runbook operacional** del cluster serenidad-platform. Provee playbooks estructurados para los 7 escenarios de incidente más probables y un procedimiento de recuperación total ante la pérdida del nodo.

### Métricas objetivo

| Métrica | Objetivo |
|---|---|
| **RPO** (Recovery Point Objective) | ≤ 5 minutos de datos perdidos (WAL archiving en Backblaze B2) |
| **RTO** (Recovery Time Objective) | ≤ 60 minutos para recuperación total del cluster desde cero |
| **MTTR** (Mean Time To Recover) | ≤ 15 minutos para incidentes del Tipo A–E (sin pérdida de nodo) |

## Parte 1 — Guía de Troubleshooting

### Escenario A: El nodo aparece como `NotReady`

**Síntoma:** `kubectl get nodes` muestra `NotReady` o no responde.

```bash
# ── Diagnóstico desde kubectl ─────────────────────────────────────────────────
kubectl describe node serenidad-prod-01 \
  | grep -A 30 "Conditions:"
# Buscar: DiskPressure, MemoryPressure, PIDPressure, NetworkUnavailable, Ready=False

# Si DiskPressure=True: el disco está lleno. Identificar qué consume espacio:
kubectl exec -n serenidad-data serenidad-pg-1 -- df -h
# Los WAL logs pueden llenar el disco si el archiving a B2 está fallando

# ── Diagnóstico desde Talos (si kubectl no responde) ─────────────────────────
source .envrc  # Cargar FLOATING_IP

# Estado del servicio kubelet
talosctl service kubelet --nodes ${FLOATING_IP}

# Si kubelet está en "Failed" o "Restarting":
talosctl service kubelet restart --nodes ${FLOATING_IP}

# Logs de Talos del kernel (panic, OOM killer, errores de disco)
talosctl dmesg --nodes ${FLOATING_IP} | tail -50

# Estado completo del sistema
talosctl health --nodes ${FLOATING_IP}

# ── Verificar acceso al VPS desde Hetzner Cloud ───────────────────────────────
# Si talosctl tampoco responde, verificar en el panel de Hetzner que el VPS
# no está en Maintenance o que no tuvo un hardware failure.
# Usar la consola web de Hetzner (VNC) para diagnóstico de último recurso.
```

**Resolución más común:** Si `DiskPressure`: limpiar WAL logs acumulados o ampliar el disco en Hetzner. Si `NotReady` sin presión de recursos: `talosctl service kubelet restart`.

### Escenario B: FluxCD no reconcilia (cambios en Git no se aplican)

**Síntoma:** Se hizo push a `main` pero el cluster no refleja los cambios después de 10 minutos.

```bash
# ── Estado general de FluxCD ──────────────────────────────────────────────────
flux get all -A

# ── Identificar el objeto específico que falla ───────────────────────────────
flux get all -A --status-selector ready=false
# Puede ser: GitRepository, Kustomization, HelmRelease, o HelmRepository

# ── Si la GitRepository no está sincronizando ─────────────────────────────────
flux get source git flux-system
# Si Ready: False → revisar la conectividad con GitLab

# Forzar re-sync del source
flux reconcile source git flux-system

# Verificar que el Deploy Key tiene acceso de lectura al repositorio
# (GitLab → Repository → Settings → Deploy Keys)
kubectl get secret flux-system -n flux-system -o jsonpath='{.data.identity}' \
  | base64 -d \
  | ssh-keygen -l -f /dev/stdin
# Debe mostrar la fingerprint de la clave registrada en GitLab

# ── Si una Kustomization específica falla ─────────────────────────────────────
flux get kustomization flux-system
kubectl describe kustomization flux-system -n flux-system | grep -A 20 "Status:"

# Forzar reconciliación completa
flux reconcile kustomization flux-system --with-source

# ── Si un HelmRelease falla ────────────────────────────────────────────────────
kubectl describe helmrelease kratos -n serenidad-core | grep -A 30 "Status:"
flux get helmrelease -A

# Re-intentar la instalación del HelmRelease (útil si falló por timeout de red)
flux reconcile helmrelease kratos -n serenidad-core
```

### Escenario C: cert-manager no renueva el certificado TLS

**Síntoma:** `https://api.sereni.dad` retorna error de certificado expirado o `kubectl describe certificate` muestra `False`.

```bash
# ── Estado de los certificados ───────────────────────────────────────────────
kubectl get certificate -A
kubectl get certificaterequest -A
kubectl get order -A     # ACME orders
kubectl get challenge -A # ACME challenges

# ── Describir el certificado específico ──────────────────────────────────────
kubectl describe certificate api-sereni-dad-tls -n traefik
# Buscar en "Events:" el mensaje de error

# ── Causas más comunes y resolución ──────────────────────────────────────────

# CAUSA 1: Puerto 80 bloqueado por el Hetzner Firewall
# Let's Encrypt HTTP-01 ACME challenge requiere TCP 80 accesible desde Internet
# Verificar en Hetzner Cloud Console → Firewall → que port 80 tiene source 0.0.0.0/0
hcloud firewall describe serenidad-prod-fw \
  | grep -A 5 "Port: 80"

# CAUSA 2: DNS no apunta al Floating IP correcto
source .envrc
dig api.sereni.dad +short
# Debe mostrar: ${FLOATING_IP}

# CAUSA 3: ClusterIssuer en estado NotReady
kubectl describe clusterissuer letsencrypt-prod | grep -A 10 "Status:"
# Si el ACME account no está registrado, recrear el ClusterIssuer

# CAUSA 4: El challenge está pendiente (normal durante la validación)
kubectl describe challenge -A
# Si está en "Pending" > 5 min: posible bloqueo de red

# ── Forzar renovación manual ─────────────────────────────────────────────────
# Borrar el certificado actual; cert-manager lo recreará automáticamente
kubectl delete certificate api-sereni-dad-tls -n traefik
# cert-manager detectará que el secret referenciado existe pero el Certificate no,
# y creará uno nuevo en ~30 segundos
```

### Escenario D: CloudNativePG no levanta (PostgreSQL caído)

**Síntoma:** `kubectl get cluster -n serenidad-data` muestra `Failing` o los pods de postgres no arrancan.

```bash
# ── Estado del cluster de PostgreSQL ─────────────────────────────────────────
kubectl get cluster,pod -n serenidad-data
kubectl describe cluster serenidad-pg -n serenidad-data | grep -A 30 "Status:"

# ── Logs del pod de PostgreSQL ────────────────────────────────────────────────
kubectl logs -n serenidad-data serenidad-pg-1 --all-containers=true | tail -100

# ── Verificar los PVCs (Persistent Volume Claims) ────────────────────────────
kubectl get pvc -n serenidad-data
# Si un PVC está en "Pending": problema con el storage class local-path
# Si un PVC está en "Lost": el volumen físico fue eliminado (situación crítica)

# ── Causa: PVC en Pending ─────────────────────────────────────────────────────
kubectl describe pvc -n serenidad-data
# Si el mensaje dice "no matching PersistentVolumes": revisar disco del nodo
talosctl df --nodes ${FLOATING_IP}

# ── Causa: Datos corruptos (raro, pero posible tras power failure) ────────────
# CloudNativePG tiene recovery automático. Si el cluster lleva > 5 min en Failing:
kubectl delete pod serenidad-pg-1 -n serenidad-data
# CNPG lo recreará y ejecutará recovery automático del WAL

# ── Verificar WAL archiving hacia B2 ─────────────────────────────────────────
kubectl exec -n serenidad-data serenidad-pg-1 -- \
  cat /controller/log/postgres.log | grep -i "archive" | tail -20
```

### Escenario E: Kratos o IAM Service retornan errores 500

**Síntoma:** El login falla, los usuarios no pueden autenticarse, o el health check de `/ready` retorna `503`.

```bash
# ── IAM Service ───────────────────────────────────────────────────────────────
kubectl logs deployment/iam-service -n serenidad-core --since=5m \
  | grep -E "error|Error|FATAL|panic"

# Si hay errores de conexión a PostgreSQL:
#   "dial tcp: connection refused" → verificar NetworkPolicy (HU-10.1A) y estado de CNPG
# Si hay errores de conexión a Kratos Admin:
#   "connection refused" → verificar que Kratos esté Running

# ── Kratos ────────────────────────────────────────────────────────────────────
kubectl get pods -n serenidad-core | grep kratos
kubectl logs deployment/kratos -n serenidad-core --since=5m \
  | grep -E "error|level=error|database|dsn|panic"

# Si hay errores de DSN/conexión a DB:
kubectl exec -n serenidad-core deployment/kratos -- \
  wget -qO- http://localhost:4434/health/ready 2>&1
# {"status":"ok"} = Kratos está bien internamente

# Si los logs muestran migración pendiente:
kubectl get job -n serenidad-core | grep kratos
# Un Job de automigration fallido puede bloquear el arranque

# ── Verificar la cadena completa ─────────────────────────────────────────────
# BFF → IAM:
curl -s https://api.sereni.dad/bff/health
# IAM Health (sin JWT, vía Traefik IngressRoute directo):
curl -s https://api.sereni.dad/api/iam/health
# Kratos public:
curl -s https://api.sereni.dad/auth/health/ready
```

### Escenario F: Traefik — rutas retornan 404 o no balancean

**Síntoma:** `https://api.sereni.dad/api/...` retorna 404 o "no such host".

```bash
# ── Verificar IngressRoutes activas ───────────────────────────────────────────
kubectl get ingressroute -A
kubectl describe ingressroute iam-service -n serenidad-core

# ── Abrir el dashboard de Traefik para diagnóstico visual ─────────────────────
kubectl port-forward -n traefik daemonset/traefik 9000:9000 &
# Abrir http://localhost:9000 → Dashboard → HTTP → Routers
# Buscar la ruta problemática y verificar el estado (OK/Error)
# Verificar los Services y Middlewares que usa la ruta

# ── Verificar que el Service de K8s existe y tiene endpoints ──────────────────
kubectl get service iam-service -n serenidad-core
kubectl get endpoints iam-service -n serenidad-core
# Si "Endpoints: <none>": el Pod no tiene la label que el Service selecciona
# Verificar: kubectl get pod -n serenidad-core -l app=iam-service

# ── Verificar que el Pod de Traefik está en Running ───────────────────────────
kubectl get pods -n traefik
# Si el Pod está en CrashLoopBackOff: revisar logs
kubectl logs -n traefik daemonset/traefik --since=10m

# ── Verificar la conectividad directa al Pod (bypaseando Traefik) ─────────────
kubectl port-forward -n serenidad-core deployment/iam-service 8888:8080 &
curl -s http://localhost:8888/health
# Si responde: el problema está en Traefik o la IngressRoute
# Si no responde: el problema está en el Pod
```

### Escenario G: Pipeline de GitLab CI/CD falla

**Síntoma:** El pipeline falla después de un push. Producción no se actualiza.

```bash
# ── Verificar el estado del pipeline via glab CLI ────────────────────────────
glab ci view
glab ci status

# ── Si falla test-iam (errores en los tests) ──────────────────────────────────
# Los errores se muestran en la salida del job. Ejecutar localmente:
cd services/iam
go test -v -race ./... 2>&1 | tail -30

# ── Si falla build-push-iam (error de Docker o push al registry) ─────────────
# Causas comunes:
# - El Container Registry está deshabilitado en el proyecto de GitLab
#   Ir a: Settings → General → Visibility → Container Registry
# - El runner no puede conectarse al registry (timeout de red del runner)
#   Reintentar el job desde la UI de GitLab

# ── Si falla el git push del bot (error de permisos) ─────────────────────────
# El CI_JOB_TOKEN necesita permisos para hacer push a main
# Ir a: Settings → Repository → Protected Branches → main
# Verificar que "Allowed to force push" está deshabilitado pero que el bot
# puede hacer push. En GitLab CI, CI_JOB_TOKEN tiene acceso por defecto
# si el proyecto tiene "Allow access to this project with the CI_JOB_TOKEN" habilitado.

# ── Si falla deploy-bff o deploy-web (error de wrangler) ─────────────────────
# Verificar que las variables CI/CD están configuradas
glab variable list | grep CF_
# Si faltan: glab variable set CF_API_TOKEN --value "<token>" --masked
```

## Parte 2 — Tabla de archivos críticos y su disposición

| Archivo | En Git | Cifrado con SOPS | Impacto si se pierde |
|---|---|---|---|
| `talos/secrets.yaml` | **NO** | No | **Crítico.** Sin este archivo no se puede administrar el OS de Talos ni regenerar el kubeconfig. Guardar en password manager. |
| `talos/talosconfig` | **NO** | No | Pérdida de acceso al OS. Se puede regenerar con `talosctl gen config` si se tiene `secrets.yaml`. |
| `~/.kube/config` | **NO** | No | Pérdida de acceso a K8s. Se puede regenerar con `talosctl kubeconfig` si se tiene `talosconfig`. |
| `~/.config/sops/age/keys.txt` | **NO** | No | **Crítico.** Sin la clave privada age es imposible descifrar cualquier secreto del repositorio. Backup en bóveda externa es obligatorio. |
| `infra/secrets/.sops.yaml` | SÍ | No | Inofensivo. Solo contiene la clave pública age. |
| `infra/secrets/**/*.yaml` | SÍ | **SÍ (age)** | Seguros en Git. Solo son descifrados con la clave privada en `keys.txt`. |
| `infra/apps/**/*.yaml` | SÍ | No | Manifiestos de K8s. Sin información sensible. |

**Instrucción obligatoria:** Los tres archivos marcados como "Crítico" deben estar respaldados en un password manager offline (Bitwarden, 1Password, o similar) antes de considerar el sistema en producción.

## Parte 3 — Playbook de Disaster Recovery Total (pérdida del nodo)

**Escenario:** El nodo Hetzner CX32 es destruido irreversiblemente (fallo de hardware, corrupción total, eliminación accidental). Todo el estado efímero del cluster se pierde.

**Datos garantizados (no se pierden):**
- Base de datos: recuperable desde backups en Backblaze B2 hasta RPO ≤ 5 min
- Código y configuración: en GitLab (Git)
- Secretos: en GitLab (cifrados con SOPS) + en password manager (claves)

```bash
# ═══════════════════════════════════════════════════════════════════════════════
# FASE 1: Aprovisionar nuevo VPS (~5 min)
# ═══════════════════════════════════════════════════════════════════════════════

# 1. Crear nuevo VPS en Hetzner (CX32, misma región, Ubuntu para rescue)
hcloud server create \
  --name serenidad-prod-01 \
  --type cx32 \
  --image ubuntu-24.04 \
  --location nbg1 \
  --ssh-key serenidad-admin

# 2. Asignar el Floating IP existente al nuevo VPS
source .envrc
hcloud floating-ip assign ${HCLOUD_FLOATING_IP_ID} serenidad-prod-01

# 3. Aplicar el Hetzner Firewall existente al nuevo VPS
hcloud server add-to-firewall serenidad-prod-01 serenidad-prod-fw

# ═══════════════════════════════════════════════════════════════════════════════
# FASE 2: Instalar Talos Linux (~10 min)
# Seguir HU-02.2 (T-02.2.3 en adelante): modo rescue, flash de imagen, reboot
# ═══════════════════════════════════════════════════════════════════════════════

# 4. Activar modo rescue en el nuevo VPS y flashear la imagen de Talos
# (Seguir los pasos exactos de HU-02.2)

# 5. Aplicar el machineconfig (usando los secrets de Talos guardados en PM)
talosctl apply-config \
  --nodes ${FLOATING_IP} \
  --insecure \
  --file talos/controlplane.yaml

# 6. Bootstrap etcd (SOLO UNA VEZ en el nuevo cluster)
talosctl bootstrap --nodes ${FLOATING_IP}

# 7. Generar el kubeconfig
talosctl kubeconfig --nodes ${FLOATING_IP} --force
export KUBECONFIG=~/.kube/config

# Verificar que K8s responde
kubectl get nodes
# serenidad-prod-01   Ready   control-plane   Xm   v1.33.x

# ═══════════════════════════════════════════════════════════════════════════════
# FASE 3: Bootstrap FluxCD y restaurar GitOps (~10 min)
# ═══════════════════════════════════════════════════════════════════════════════

# 8. Recrear el secret de SOPS con la clave age del password manager
kubectl create namespace flux-system
kubectl create secret generic sops-age \
  --namespace flux-system \
  --from-file=age.agekey=~/.config/sops/age/keys.txt

# 9. Bootstrap FluxCD contra el repositorio GitLab
source .envrc
flux bootstrap gitlab \
  --owner serenidad \
  --repository serenidad-platform \
  --branch main \
  --path infra/clusters/serenidad-prod \
  --token-auth \
  --token ${GITLAB_TOKEN}

# FluxCD comenzará a reconciliar todo el estado del repositorio:
# - Helm repositories y releases (Traefik, cert-manager, Kratos, CNPG, CCM)
# - Kustomizations (namespaces, NetworkPolicies, Deployments)
# El proceso completo toma ~10-15 minutos en el primer ciclo

# Observar el progreso
watch flux get all -A

# ═══════════════════════════════════════════════════════════════════════════════
# FASE 4: Restaurar la base de datos desde Backblaze B2 (~15-30 min)
# ═══════════════════════════════════════════════════════════════════════════════

# 10. Esperar a que CloudNativePG operator esté instalado y Running
kubectl wait deployment/cnpg-controller-manager \
  -n cnpg-system \
  --for=condition=Available \
  --timeout=300s

# 11. Listar los backups disponibles en B2
kubectl get backup -n serenidad-data
# Si el Cluster de PostgreSQL aún no existe (FluxCD lo crea automáticamente),
# esperar a que FluxCD aplique el HelmRelease de CloudNativePG

# 12. Realizar Point-in-Time Recovery desde el último backup
# Editar temporalmente el Cluster CRD para especificar el backup de restauración
# (Ver HU-05.2 para el procedimiento exacto de PITR)

# El Cluster de CNPG con recovery configurado descargará el base backup de B2
# y aplicará los WAL segments hasta el RPO deseado

# Verificar que la restauración completó
kubectl get cluster -n serenidad-data serenidad-pg
# STATUS: Cluster in healthy state (o Ready)

# Verificar conexión a la base de datos
kubectl exec -n serenidad-data serenidad-pg-1 -- \
  psql -U serenidad_admin -d iam_db -c "SELECT COUNT(*) FROM user_profiles;"
# Debe retornar el número de registros esperado (cercano al RPO de 5 min)

# ═══════════════════════════════════════════════════════════════════════════════
# FASE 5: Verificación end-to-end (~5 min)
# ═══════════════════════════════════════════════════════════════════════════════

# 13. Verificar que todos los servicios están en Running
kubectl get pods -A | grep -vE "Running|Completed|Succeeded"
# No debe haber pods en estado problemático

# 14. Verificar los health endpoints
curl -s https://api.sereni.dad/api/iam/health
# {"status":"ok","service":"iam-service",...}

curl -s https://api.sereni.dad/auth/health/ready
# {"status":"ok"}

curl -s https://app.sereni.dad | grep -c "qwik-"
# > 0 (la SPA Qwik está sirviendo HTML con hydration state)

# 15. Verificar TLS
curl -sI https://api.sereni.dad | grep -i "strict-transport-security"
# Debe mostrar HSTS header

# 16. Actualizar el Hetzner Firewall con la IP actual del administrador
./scripts/update-firewall.sh
```

**Tiempo total estimado de recuperación:** 35–50 minutos desde cero hasta servicio completamente operacional.
